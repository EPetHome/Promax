## 一、目标

在 dsh 上用**一个最小插件**和**一个脚本假模型**，验证三件事：

1. **fork 能触发**：调用 `Skill` 时，声明了 `context: fork` 的技能会起一个**独立子会话**去执行，执行完返回 WorkBuddy 同款首行 `Skill "<名>" completed (forked execution).`；没声明的技能（内联）只返回说明正文，不起子会话。
2. **派发到回报的链路能走通**：Lead 调 `TeamCreate`、`Agent` 派出一个常驻成员 → 成员调 `Skill` 触发 fork → 子会话写文件、回答 → 成员用 `send_message` 回报 → Lead 被叫醒、收尾。
3. **剧本可重复**：同一剧本跑两次，工具调用序列一致。

全程由脚本假模型决定每一步，不联网、不花钱。这是可行性验证：某项做不到就如实写原因，**不要改 dsh、不要换成真实模型绕过去**。

## 二、背景（先看懂现状）

Promax 要让专家团 2.1.5 原样跑在 dsh 上。2.1.5 是按 WorkBuddy 写的，依赖 WorkBuddy 的 `Agent`、`Skill`（fork 执行）等工具；dsh 没有这些。第 2 轮真跑发现：技能在 dsh 上不会 fork，Lead 会自己抢活，模型还会编造「completed」回执。动手写正式兼容层之前，先用最小代价确认 fork 和链路在 dsh 上做得出来。

### 6.2 最小插件 `wb-mini`

| 工具 | 参数 | 行为 | 返回 |
|---|---|---|---|
| `TeamCreate` | `team_name`、可选 `description` | 只登记团队名 | 一行成功文本，写明团队名 |
| `Agent` | `description`、`name`、`prompt`、`subagent_type` | 按 `subagent_type` 在名册里找成员，用 `ctx.subagents.startContinuable` 起常驻成员（spawn 提供方，persona 用名册），首条消息是 `prompt`；未建团时自动建团 `_auto_<uuid>`；名册里没有的类型返回错误 | WorkBuddy 同款 `Spawned successfully.` 多行文本（字段同 2.2） |
| `Skill` | `skill`、可选 `args` | 在配置的技能根目录里按 frontmatter 的 `name` 找技能。**有 `context: fork`**：用 `ctx.subagents.start('spawn', …)` 起一次性子会话，任务内容 = `Base directory for this skill: <目录>\n<正文>`，有 `args` 时追加一段写明参数；等它结束。**没有**：不起子会话 | fork：`Skill "<名>" completed (forked execution).` + 空行 + 子会话最终回答；内联：`Base directory for this skill: <目录>\n<正文>` |

技能根目录、名册路径、成员模型都写在 profile 的 `config` 里，不写死在代码中。

### 6.3 脚本假模型 `scripted-llm`

注册服务商 `scripted`、型号 `script-v1`（照 llm-replay 的 `ReplayAdapter` 写法），profile 的默认模型与成员模型都用它。它根据**请求内容**判断角色和进度，按下表出牌（每次回复只出一个动作）：

| 角色（靠标记识别） | 剧本 |
|---|---|
| Lead（系统提示含「【先遣Lead】」） | 第 1 次：调 `TeamCreate {team_name:"xq-team"}`；拿到结果后：调 `Agent {subagent_type:"probe-member", name:"probe-member", description:"先遣", prompt:"请调用 probe-fork 技能，参数为 XQ-42，然后用 send_message 把结果回报给我"}`；拿到 Spawned 结果后：回复文字「已派发，等待回报」结束本轮；**被叫醒后**（收到成员消息或结算通知）：回复文字「收到回报：<回报里的关键字>」结束 |
| 成员（persona 含「【先遣成员】」） | 第 1 次：调 `Skill {skill:"probe-fork", args:"XQ-42"}`；拿到结果后：调 `Skill {skill:"probe-inline"}`；再拿到结果后：调 `send_message` 给 Lead，内容含 fork 结果首行和子会话写的文件路径；之后回复文字结束 |
| fork 子会话（首条消息含「Base directory for this skill」和 probe-fork） | 第 1 次：调 `write`，在运行目录写 `fork-output.txt`，内容含参数 `XQ-42`；之后回复文字「FORK-DONE XQ-42」结束 |

假模型把每次被调用的角色、判定依据和出的牌追加到 `<运行目录>/scripted-llm.jsonl`。遇到剧本外的情况（识别不出角色、步骤对不上），回复一段以「【剧本外】」开头的文字并记录，不要乱出牌。

## 七、设计约束（陷阱）

1. **委派深度**：成员（深度 1）再起子会话就是深度 2，dsh 默认上限是 1。在本测试 profile 里把需要的上限放开；起不来就如实记录报错原文。
2. **角色识别别靠顺序**：靠标记文字判断，同一角色的进度靠请求里已有的工具结果判断。
3. **Lead 被叫醒的那一次**：请求里会出现成员消息或结算通知，剧本要据此判断，不能当作第 1 次。
4. **不要用 headless 运行器**：它会在 Lead 第一次空闲时退出（第 1 轮的教训），一定用常驻运行器副本。
5. **消息 source**：插件给模型注入任何消息时 source 写 `{kind:'plugin:<插件名>'}`。
