## 七、设计约束（陷阱）

1. **会话目录名以 `--` 开头**：解压要用 Python `subprocess.run(['zstd','-dcf','--',path])`，不能直接 `zstd -d 路径`。会话在 `promax-project/dsh-home/sessions/--Users-Admin-Desktop-Promax-promax-project-runs-<编号>--/<会话>/session.v4.jsonl.zstd`。
2. **Lead 和成员的区分**：Lead 会话 id 以 `session-` 开头；成员子会话原文里有「成员 xxx」。pi 结果里的「成101」是指成员会话的 seq 101。
3. **`run.sh` 的外层退出码 0 不代表 dsh 成功**：以 `timing-*.json` 的 `exit_code` 和会话 `turn/end` 为准。
4. **`LATEST` 不是改动前基线**：A1 必须用 `.bak/20260926-115838`。
5. **文本匹配会被格式挡住**：Markdown 加粗、中英文引号不同，都会让字符串匹配不上。「没匹配上」不等于没有、也不等于编造，要人工确认。
6. **Lead 抢救保存 ≠ 成员无错**：成员报错后 Lead 自己补写或重派，成果虽然在，但报错事实要照记。反过来，也不能因为成员报过错，就把 Lead 的正确披露判成红项。
7. **pi 分析 JSON 只能当索引**：`分析-09b/02-analysis.json` 可以用来快速定位 seq，但每个你写进结论的数都要从会话原文重算。
8. **进程检查**：用 `pgrep -f "[.]bin/dsh --profile"`（不加方括号会把检查命令自己也匹配进去）；记录命令本身的返回码。

## 八、工作习惯

- 先写脚本 `promax-eval/分析-09-复核/01-extract.py`，把 9 个运行目录的全部会话解压成统一的调用表（运行、会话、角色、seq、工具名、参数、结果首行、报错），落成 JSON；后面的判定都从这张表算，别每项重新解压。

- 行文按项目约定：结论先行、表格、短句、带 🟢🟡🔴⚪；少用缩写和内部术语。
