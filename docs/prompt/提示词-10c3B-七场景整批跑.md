## 七、设计约束（陷阱）

1. 会话目录名以 `--` 开头，解压用 `subprocess.run(['zstd','-dcf','--',path])`；以 `timing-*.json` 的 `exit_code` 和 `turn/end` 判成败。
2. **报错全表**：扫全部 `tool/result`，含 `Traceback`、`Error:`、非 0 退出、`"accepted": false` 的都记，即使后面成功了；A 组新增的拒绝（草稿被拒上限、第 3 轮预检拒绝、删组拒绝、`--previous` 拒绝、被审文件改动拒绝）各自单列——**它们被触发不等于失败**，要看 Lead 之后是否按规则处理。
3. 你的上下文只有 272K：会话一律用脚本汇总，不要把整段会话打印进对话。
4. flow_check 的判定是线索不是结论；与原始会话冲突时以会话为准，并在交付里写明。
5. **不能「结束回合等通知」**：`pi -p` 下结束回合就是结束会话，没有人会再叫醒你，还在跑的后台任务会被杀掉（Claude 09-30 晚复现：`bg_run` 后回一句「等待完成通知」，12 秒后 pi 以退出码 0 退出，任务被杀）。等待一律用第六章第 3 步的脚本。上一次中断时，3 个场景进程在会话结束后仍无人看管地跑完了——所以收尾前务必确认没有残留的 dsh 进程和后台任务。
