# 工作方式与复核规范（用户 2026-09-26 定，长期有效）

> **复核方 = GPT6-Astra**（用户 09-26 更正：不是 Codex）。本文中凡写「Codex」的角色名，都指复核方 GPT6-Astra；R08-2 等历史记录里的 Codex 是当时的实际复核方，不改。

📍 **用户拍板 → Claude 出谋划策、派工 → pi（GPT6-Sol / DeepSeek4.1-Flash）写代码、跑测试 → GPT6-Astra 复核（调试轮轻量 / 节点轮全量，§2.7）→ Claude 阅读复核结论、向用户汇报。** Claude 不写代码，也不逐条做证据复核；Astra 不开发、不定方向，只复核。主线纪律（开工卡、建议标注、守节点、轮次、分流、状态行）写死在项目根 `CLAUDE.md` / `AGENTS.md`。

## 1. 分工

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 用户 | 定目标、拍板范围、启动 pi 和 Astra；并守住 5 件事：① 开工前确认开工卡（尤其「不追求」「轮次」）② 拍板时「可以」带范围，只批 [主线必需] ③ 只有用户能宣布过节点，上一节点没绿不开下一个 ④ 轮次到了就停下讨论 ⑤ 新事当场定去处（①②③④） | 读证据、读长结果、选模型、判 pi 对错（交给 Astra 与 Claude） |
| Claude（Opus） | 出方案和理由；写任务书，**开工时一次写好执行与复核两份 pi 提示词**和串联启动命令；按难度选 pi 的模型和思考档位；阅读 Astra 结论，向用户汇报并提下一步 | 不写产品代码；不做逐条证据复核（只在结论互相矛盾或会影响拍板时抽查） |
| pi（Sol / ds4.1） | 按提示词改代码、改配置、真跑、写结果文件 | 不自己定范围；不自己判通过 |
| GPT6-Astra（复核方） | 独立复核 pi 的结果；节点轮还要审 **Claude 的规格本身**；把结论写进唯一结果文件 | 不开发；不改 `promax-project/`；不启动新运行；不定方向、不扩大范围 |

```text
用户拍板 ─→ Claude：一次写好两份提示词 + 一条串联启动命令（§2.8）
                 执行：docs/prompt/提示词-<轮>.md（Sol / ds4.1）
                 复核：docs/prompt/复核-<轮>.md（Astra）
               ↓ 用户粘贴命令（唯一一次启动）
            pi(Sol/ds4.1)：执行、真跑、写 pi 结果 → 用户退出会话
               ↓ 自动接着启动
            pi(Astra)：先确认执行已完成 → 独立复核 → 唯一结果文件 R<任务>-<序号>
               ↓ 用户告诉 Claude「复核完了」
            Claude：读结论 → 更新 5 行与主线图 → 向用户汇报 → 提下一步
```

**一条硬规则**：执行和复核不能是同一方。pi 的自检、pi 结果里的「全部通过」都只算线索，不算证据。

## 2. Codex 复核要求（每轮都照这个做）

### 2.1 输入

**复核提示词在开工时与执行提示词一起写好**（用户 2026-09-28 定），放 `Promax/docs/prompt/复核-<轮>.md`。它只有这一份：既是派单，也是直接给 Astra 的 pi 提示词，不再另写「复核派单」或「提示词-<任务>复核.md」。内容按 §4 模板：复核级别；当前主线和本轮明确不做的事；任务书、执行提示词、**预先指定的** pi 结果路径、答案或参考值的位置；本轮验收表；特别关注。

因为写在执行之前，复核提示词不能写死运行编号或结果数字，只写路径与规则，由 Astra 从 pi 结果和原始记录里自己找。执行中途如果有追加指令改了范围，由 Claude 在同一份复核提示词末尾补一段「追加」，再由用户启动复核。

### 2.2 必做

1. **先确认 pi 真的跑完**：pi 结果文件已写出、没有 dsh 进程在跑、每个运行目录都有 timing。没跑完就停下，报告现状。
2. **证据只认会话记录和产物**：会话、产物、保存回执、diff；不采信 pi 的汇报原话。
3. **逐项核对本轮验收表**：每项 🟢 / 🟡 / 🔴 / ⚪，附证据位置。
4. **核对 pi 报告**：哪些说法成立、哪些说过头、哪些是 pi 发现而你没发现的。
5. **审规格本身**：Claude 写的提示词、验收标准里有没有错误、自相矛盾、不适用的标准。单列一节，写明影响。（这是 Claude 自己复核时看不到的盲区。）
6. 区分事实、推断、未知；每个场景只跑一次时标明「n=1」；不把「能跑通」写成「能力可靠」。

### 2.3 不做

- 不改 `promax-project/**`、答案、pi 结果原件；不启动 dsh、pi、浏览器、服务。
- 不偏离派单写明的主线。与主线无关的观察可以记录，但放在「其他观察」，不排成下一步。
- 不打印凭据；不读 `~/.dsh-promax-first/**`；不动 `old-version/**`。

### 2.4 输出

写进唯一结果文件，新增一段 `R<任务号>-<序号>`：

| 部分 | 要求 |
|---|---|
| **结论页（放最前，一页以内）** | 一句话结论；验收表（🟢🟡🔴⚪）；规格问题；需要用户拍板的点（最多 3 个） |
| 证据与明细 | 放在结论页后面，或放 `promax-eval/分析-<任务>-复核/` 里，结果文件只留链接 |
| 写法 | 结论先行、表格、短句；少用缩写和内部术语；不写推导过程 |
| 同步 | 新问题登记问题总表（接着现有编号）；基线 §0.2「能力认知」只改有证据的行；任务书分步表更新状态 |
| 下一步 | 只写建议，标明「建议」，由用户拍板 |

### 2.6 判分口径（用户 2026-09-28 定，沿用旧评测集 promax-16-v1）

| 规则 | 内容 |
|---|---|
| 状态分开 | PASS / FAIL / RUN_ERROR / ENV_BLOCKED / SETUP_BLOCKED / NOT_RUN / NEEDS_REVIEW / USER_STOPPED；没执行或缺证据不填 PASS |
| 能力与环境分开 | 网关、上游、额度等基础设施问题单列，不计入能力分数，也不从分母里删掉 |
| 单次与稳定分开 | Pass¹（单次通过）与同一用例多次全过分别统计，只报原始分子分母；n 小不代表稳定 |
| 不采信内置结论 | 以会话记录和产物为准，不以 Judge 或 pi 的自评为准 |
| Judge 三类校准 | 合格对照（测误报）、已知缺陷与返修（测检出）、证据不足（测 INCOMPLETE）分别记录 |
| 用量分开 | 耗时、token 按 Lead / 业务成员 / Judge 分开记 |
| 得分表 | 每轮复核后在基线 §4.3 追加一行 |

### 2.7 复核分两级（用户 2026-09-28 定，方案 B）

```text
【调试轮】本轮不宣称过节点
  Claude 提示词 → pi 执行并附原始证据（会话路径、产物、命令输出）
     → Astra 轻量复核：只核本轮验收表与原始证据，不审规格；结论 ≤10 行
     → Claude 汇报 → 下一轮（结果只当线索，不改基线 §0.2 能力认知）

【节点轮】宣称「7/7」「N? 完成」，或要改基线结论
  Claude 两份提示词 → pi 执行 → 自动接复核
     → Astra 全量复核（按 §2.2 全部必做，含审 Claude 规格）
     → Claude 汇报 → 用户拍板过节点
```

复核提示词第一行写明本轮是「调试轮」还是「节点轮」。调试轮中途发现像是已过节点，也不直接宣布，另开一轮节点轮全量复核。

| 规则 | 内容 |
|---|---|
| 怎么衔接 | 执行会话用 `/quit` 正常退出时 pi 返回 0（09-28 核对 pi 源码：交互退出 `process.exit(0)`），`&&` 自动启动复核；执行中途用户照常可以和 pi 对话 |
| 执行没跑完 | 复核第一步按 §2.2-1 检查；pi 结果不存在或仍有 dsh 进程 → 只写「执行未完成」和现状，停止，不做复核 |
| 不想自动复核 | 退出执行会话后，在「10 秒后自动开始」提示期间按 Ctrl+C。🔴 不要指望在 pi 里按 Ctrl+C 中断整条命令：pi 自己接管 Ctrl+C，退出仍返回 0，复核照样会启动 |
| pi 崩溃 | 崩溃返回 1，复核不会启动；用户单独粘贴后半段即可 |
| 不用后台轮询 | 不让 Astra 开着会话等待执行结束（耗时、易超时）；衔接只靠这条命令 |
| 10c-3 试行调度脚本（用户 09-30 定，任务 10 D19—D22） | 需要「评审不过自动退回返修」的轮次，用 `docs/prompt/调度-10c3.sh` 代替串联命令：非交互模式（`pi -p`）轮流启动 Sol 与 Astra，每次新会话，靠交接区文档（`promax-eval/交接-10c3/`）传递；到上限自动停。仍不让 Astra 挂着轮询。试行结果记入 R10-7「流程检查」，好用再写成通用规则 |

**首次使用检查（新流程第一轮必做，结果记进本轮结果文件「流程检查」一节）**：

| # | 检查 | 通过标准 |
|---|---|---|

| 2 | Astra 第 0 步是否先确认执行已完成 | 会话里先查 pi 结果文件与 dsh 进程，再开始复核 |

### 2.5 已验证的复核方法

| 要核对什么 | 怎么取 |
|---|---|
| 解压会话 | `promax-project/dsh-home/sessions/<按 cwd 命名的目录>/<会话>/session.v4.jsonl.zstd`；目录名以 `--` 开头，要用 Python `subprocess.run(['zstd','-dcf','--',path])` |
| Lead 与成员 | Lead 会话 id 以 `session-` 开头；成员子会话原文里有「成员 xxx」 |
| 每次响应的模型 | `assistant/message` 的 `data.stream` 里的 `"model"`（`request/header` 每个会话只有 1—3 条） |
| 技能目录 / 实际加载 | 某条 `user/message` 里 `- \`名\`: 描述` 列表；成员会话里 `name == "skill"` 的调用 |
| 工具清单 | `request/header` 的 `data.header.tools` |
| 报错 | `turn/end` 的 `reason.kind == "error"`；工具级报错看 `tool/result` |
| 越界 | 所有 `tool/call` 参数里的绝对路径，只允许本运行目录、`promax-project/team/`、系统路径 |
| 慢请求 | `step/start` 到 `assistant/message` 的时间差；输出不到 500 token 却超过 20 秒的，单列为尖峰 |
| 进程 | `pgrep -f "[.]bin/dsh --profile"`（不加方括号会把检查脚本自己也匹配进去）；记录命令本身是否执行成功 |
| 文本匹配 | Markdown 加粗、引号样式会挡住字符串匹配；「没匹配上」不等于编造，要人工确认 |

现成脚本：`promax-eval/复核工具/`、`promax-eval/分析-08b-复核/`。

## 3.5 开工卡与提议标注（用户 2026-09-28 定，长期有效）

**开工卡**：每个任务（及每个子轮）在任务书最前面先写这 3 行，用户确认后再写机制和提示词。

| 行 | 写什么 | 反例 |
|---|---|---|
| 做完的样子 | 用户能直接观察到的结果，例：「7 个场景各跑 1 次，流程全部走通」 | 写成机制：「派审时机为…、每版最多返修 1 轮」 |
| 本阶段不追求 | 明确不当门槛的东西，例：「Judge 能力、耗时只记录」 | 空着，任由产品总目标（可靠/成本/效率）补进来 |
| 轮次上限 | 最多几轮（每派一次 pi 执行算 1 轮）；到了停下由用户重新拍板，不自动续轮 | 不写上限，按「再修一轮」无限延续 |

**提议标注**：Claude 每次给出下一步、方案选项或多条建议时，每条必须标 **[主线必需]** 或 **[顺手优化]**，并说明服务 [06 主线图](06-主线图.md) 哪个节点。用户回「可以」时，默认只批 [主线必需]；[顺手优化] 进停车场，用户单独点名才做。

**人读 5 行**：基线入口页最顶上的「给人看的 5 行」（主线 / 现在 / 下一步 / 不追求 / 轮次）每轮复核后由 Claude 覆盖更新，大白话、不写编号术语。
