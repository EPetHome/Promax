## 1. 目标和范围

目标：减少与当前原文/程序事实矛盾的误判，保留真实缺陷；复查时能区分“成员修复了问题”和“Judge撤回原误判”。保留原有角色、版本保护、必需依据门禁及有限返修机制。

```text
冻结目标、材料和被审版本
  → 原Judge读取、对照并形成问题
  → 现有promax_check_result：程序核对可机械验证的依据
  → 真实缺陷按现有安排返修
  → 同组Judge依据当前与历史版本复查
  → 程序保存结果、问题历史及关闭原因
```

上述是现有工作流的内部职责，不增加第二个Judge、常驻审查Agent、独立审批关卡或固定追加模型回合。引用校验失败仍使用现有有限恢复，不承诺实际重试次数一定减少。

本阶段完整交付三项能力：①原文/事实一致；②结论强度与证据匹配；③复查与误判处理。三项共同验收，不能只更新提示词便宣布阶段三完成。不并入通用问题编号重构、业务说明、整体效率优化或模型选型。

## 3. 缺陷提出：用同一次提交留下可核对依据

### 3.1 Judge的判定要求

每条必须返修的问题应交代：规则来自哪里；当前成果实际断言是什么；与哪条原始证据/程序事实矛盾；影响什么、应修哪里。优先用现有evidence/impact/fix承载解释，不要求另交一篇分析报告。

- 已证实错误/遗漏：作为defect，给定向修正。
- 必需判断缺少依据：用现有evidence_gap或unverified/验收状态表达，不能判met/PASS；不虚构错误原句。
- 偏好或非必要改进：suggestion，不自动触发整篇返修。
- 必须由用户决定的取舍：沿用decisions，不让Judge代定。

程序统计证明“3星记录75条”，不证明“其中引用诉求集中”；不得把档位数量当主题频次。报告明确只作定性举例时，不反向要求它补做用户未要求的全量语义统计。

### 3.2 最小协议补充

建议只增加一组有界的原文引用信息：每项包含被审文件、定位、逐字片段；文件哈希和review_request由程序绑定，不由模型重新手填。具体字段命名在实施中与现有类型统一，不新增取证工具或通用证据框架。

复查引用可选择当前被审版本或该问题提出时的绑定版本；历史路径/哈希由程序从该问题的已存记录取得，不接收任意历史文件地址。同一套引用核对覆盖当前修复和原判断撤销。

对于声称“报告写了X/两处自相矛盾”的defect，必须有对应引用；矛盾指出两处依据。每条问题建议最多4处、每处最多400字符，超长明细沿现有只读文件入口查阅。

对于缺失内容，不能要求引用不存在的句子：改为指明适用验收要求和已检查范围；程序验证要求/文件属于当前scope，缺失是否成立仍由Judge判断。不得为了满足引用格式让成员补写无关正文。

程序在stage与权威commit共用核对：
1. 文件属于本次被审集合，实际字节与程序绑定版本一致。
2. 引文逐字存在并落在声明定位范围；重复/歧义时明确要求缩小定位，不能默认选首处。
3. 不接受模型提供的任意磁盘路径或跨任务文件；历史引用只经已有只读快照和已登记问题身份访问。
4. 输入不成立时返回有界字段错误；不把协议错误登记成成果缺陷，也不通过静默删除问题换取PASS。
5. 当前PASS、必需依据、输入版本、并发/迟到结果保护保持。

既有program_facts继续提供统计口径、record_id原因及来源身份。Judge说明数值冲突时引用同源事实；无需新建自由公式执行器，也不开放shell权限。无可机械判定的语义关系不伪装为程序已证实。

## 4. 复查：保留生命周期，增加关闭原因

建议保留open/verified/unverifiable及现有流程，为新合同下的verified增加一个关闭原因，概念值为fixed（已修复）或false_positive（原判断不成立）。新提交必须明确原因；旧记录缺失时显示“历史关闭原因未知”，不倒填已修复或误判。

| 复查结论 | 必要依据 | 处理 |
|---|---|---|
| fixed | 原问题成立，当前版的修改/证据已消除冲突 | 关闭原ID，保留原问题及修复证据 |
| false_positive | 回看提出问题时的原被审版本，原指责本来就不成立；说明当时原文/规则/事实的对照 | 同一ID记录撤回，不计作成员修复成果 |
| open | 当前仍有同一缺陷 | 保留问题，不换ID掩盖未修 |
| unverifiable | 缺必要原版本或证据，无法证明已修或原判有误 | 保留未知，不以撤销名义放行 |

**撤销误判必须核对“提出该问题时”的版本。**当前文稿已经正确，只能说明现在可能修好了，不能据此证明过去也是误判。旧快照缺失时不得拿当前正文倒推历史。

若历史同名ID曾代表不同指责、无法确定此次撤销对应哪条原问题，保留unverifiable，不仅凭ID字符串关闭；这属于本次关闭安全边界，不扩展为全套编号重构。

复查结论仍由当前获准的同组Judge提交；成员或主Agent只能提供反证，不能直接关闭问题。成员提供反证且正确正文无需修改时，可沿现有回执/交接把事实交回下一次复查，不强制改错正文来满足“做过修改”。

关闭原因进入权威记录、历史和渲染报告；修改版本后按现有规则复核适用性，撤销不表示未来该位置永不可能产生真问题。独立的新缺陷使用独立身份，本阶段不重做全套编号体系。

指标区分：已核查关闭总数、修复关闭、Judge撤回、历史原因未知。Judge自报撤回只是一个观察结果，不自动成为独立准确率真值；质量评分继续使用独立参考标签，不把撤回全部算“修复成功”。

## 6. 验收：工程与真实判断分开证明

| 必须覆盖的场景 | 预期 |
|---|---|
| 原任务7正确区分非整数/越界 | 不产生J1-01式缺陷 |
| 保留相近文本但故意把1.5归入“<1或>5” | 能指出真实分类矛盾 |
| 用75条评分档位数量宣称某诉求集中 | 保留J1-02式缺陷 |
| 改为定性举例并明确未统计主题频次 | 关闭对应真问题，不额外要求全量语义分析 |
| 引文不存在、错文件/错版本、定位歧义 | 程序拒绝该提交并指出字段，不形成有效检查结果 |
| 原问题确实是误判，正文未改 | 引用原被审版反证，记录false_positive；不记成员修复 |
| 原版有错、当前已修 | fixed，不能冒记false_positive |
| 缺旧快照、反证不足或其它真问题未修 | 保留unverifiable/open，不能整体PASS |
| 旧合同、旧记录、新合同、迟到/重复提交 | 兼容可读，保护保持，历史不改写 |

工程检查：覆盖真实注册→stage→权威commit→持久回读/报告/指标的隔离链，配合受影响类型、构建及加载身份；保留阶段二回归。合成Judge输出只能证明协议与保护，不证明Judge判断能力。

业务检查建议使用小规模、版本冻结的真实Judge对照集：上述真假成对案例加未参与规则编写的同类改写案例，评测时不把参考答案注入Judge。样本、模型/配置、规则/版本、输入、输出及失败原样保留；不只挑一次成功，不以调试样本自评分为整体准确率。

真实Judge调用本轮尚未授权或执行。实施任务需写明可用模型、样本、次数/预算与成功判据，再开展该部分。若只完成工程，交付应标“工程/静态通过，Judge效果待验”；阶段三业务完成须同时证明减少目标误报且保留目标真问题，不能只证明规则已经加载。
