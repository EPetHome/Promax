# 产品设计与验收目标

📍 **保留当前产品架构，先把评分场景的完整交付做实。**本页是已讨论设计的阅读摘要；不新增产品规则、角色、阈值或运行权限。

## 1. 稳定主线

```text
Promax：把内部产品工作做成可检查、可继续修改的成果
├─ M1｜整体产品定位与首版边界
├─ M2｜工作协作、质量与审阅机制
├─ M3｜界面与交互形式
└─ M4｜新产品的技术架构
```

| 主线 | 已确认设计 | 本阶段边界 |
|---|---|---|
| M1 | 客研、产品探索、需求管理、产品需求方案、需求评审、用户分析六类能力按需参与；默认Markdown，图和HTML按任务选择 | 评分场景不能代表全部专业能力；不固定每次调用全队 |
| M2 | 主Agent组织和派修，成员产出，Judge独立检查，程序维护事实、版本、权限和明确判定 | 不让主Agent自任Judge，不把Judge历史判断当真值 |
| M3 | 固定输入框、独立询问浮层、常驻只读成员总览、右侧材料／成果／版本查看 | 首稿可读即有入口；查看不重跑模型；阅读位置和旧版操作仍需体验证据 |
| M4 | 原件留存、按需上下文、请求健康、持久记录、版本与量化指标；组织能力复用既有系统 | 集中保存、权限共享、补传、归档、知识发布和研发回流分别验收 |

## 2. 谁负责什么

| 主体 | 责任 | 不可自动替代的事实 |
|---|---|---|
| 用户 | 目标、有效决定、范围和必要取舍 | 对原因的猜测不自动成为技术根因 |
| 主Agent | 理解、澄清、计划、派工、处理增量要求、安排返修和说明成果 | 自由总结不代替实际保存结果 |
| 业务成员 | 专业分析、产出和受托修改；引用适当证据 | 自报完成不代替持久提交或独立检查 |
| Judge | 对指定版本核查目标、证据、逻辑和旧问题 | PASS／verified不自动成为独立正确标签 |
| 程序 | 权威记录、授权、版本、机械计算、提交、状态与明确公式 | 结构齐全、哈希一致不证明所有业务语义正确 |

开发工具Pi、Codex与Promax内的这些业务角色是不同层次。开发模型设置不自动改变产品业务模型。

## 3. 完整链路与完成条件

```text
原始目标＋有效决定＋材料
         ↓
冻结当前任务／输入／验收基准
         ↓
受控事实计算 → 成员分析 → 可读首稿
         ↓
必要关联登记 → 独立评审 → 定向返修／复查
         ↓
正式版本提交 → 当前入口更新 → 真实交付说明
```

完整通过至少要求：适用必需项全部满足、核心未知和无结果为0、阻断问题已核实解决、必回查无遗漏、交付版本与被审版本一致且可读、正式保存事实成立。

执行结束、草稿存在、Judge结论、正式保存、用户当前打开的版本应分别记录，再形成对用户清楚的结论。失败可安全结束为部分完成，不无限重跑，也不猜成功。

## 4. 本阶段必须保全的六项能力

| 范围 | 预期行为 |
|---|---|
| R22 可靠统计 | 程序计算总量、有效／无效、各星级和比例；成员与Judge共享事实 |
| R23 局部修改 | 修改受影响内容；变化的依据失效并重新核验，未变内容保留，旧版可查 |
| R24 独立Judge | 集中检查适用范围；主Agent派修，原Judge逐项回查；机械事实不反复心算 |
| R25 简洁交付 | 正文保留结论、关键依据、建议和限制；普通追问只解释已有结果 |
| R26 记录与评价保全 | 开始、进度、失败、恢复、耗时、用量与评价有版本；未知不填0 |
| R27 程序消重 | 同等工作读取进度／结果；真实变化、批准恢复或明确重评才重新执行 |

来源存在、取得内容、支持结论分开；来源/结论/问题的身份与版本由程序保护。语义支持、代表性、因果等仍需Judge判断。质量、失败归因和效率不混成自由综合分。

## 5. 固定评分样本与三轮验收

材料：[v1](../../../old-version/docs/测试/Promax实测-评分样本-v1.json)、[v2](../../../old-version/docs/测试/Promax实测-评分样本-v2.json)。两份均为合成数据；仅原始数值型、非布尔、1—5整数为有效评分，不转数字字符串、不去重、不按日期过滤。

| 指标 | v1参考值 | v2参考值 |
|---|---:|---:|
| 总记录 | 320 | 320 |
| 有效／无效 | 300／20 | 300／20 |
| 1—5星数量 | 30／45／75／90／60 | 31／45／74／90／60 |
| 低星比例 | 75/300＝25% | 76/300＝25.33% |
| 高星比例 | 150/300＝50% | 150/300＝50% |
| 输入变化 | 初始数据 | T0076.rating由3变1，其余319条不变 |

依次在同一工作中进行：

1. **v1首轮。**分析评分与反馈，交付简洁Markdown；包括分布与数据质量、少量原文和record_id、三条有依据且必要时标待验证的建议、限制。仅用附件，不扩展成市场调研；可读首稿及时给入口。
2. **普通追问。**“报告里的低星比例为什么这样计算？分母为什么不是全部记录数？”预期不新增业务生成、统计或Judge；主Agent可以正常回答。
3. **v2替代。**新文件完整替代旧数据，不合并；核对差异，只更新受影响统计、表述、结论和必要关联；完成必要检查，保留旧版并说明变化。

新旧输入都留存用于对照，不等于合并计算。局部修改可以跨章节；它不等于只替换单个标题，也不等于旧稿全正确。

## 6. 效率与上下文目标

| 事项 | 已定口径／状态 |
|---|---|
| 本场景端到端 | 首轮≤5分钟，单条更新≤3分钟；需同时满足正确性、必要检查和正式保存 |
| 首稿与调度 | 首稿可见延迟≤2秒、本地获准发出≤1秒是既有试验目标；不等于端到端时限 |
| 请求健康 | 连续无有效内容30秒提示、90秒有界恢复，同一逻辑请求最多再试1次；持续生成不按90秒总时长误杀 |
| 上下文初值 | 主Agent32k/64k，成员64k/128k，Judge96k/192k；分别为整理触发／单请求工作上限 |
| 工具和经验 | 单工具4k、同批8k；经验最多3条且合计1.5k；全文留存可回读 |
| 当前限制 | 端点C/R与估算误差未核实，新的硬限制未启用；当前摘要触发也受该条件影响 |
| 简洁体量 | 800—1500中文字符是外部提出的试验建议，尚未被确认为硬指标 |

八组指标仍为Q1/Q2质量与关键上下文、D1/L1首稿及执行等待、R1/J1故障恢复及评审返修、C1/C2请求上下文与累计用量。指标R1与返修编号不是同一体系。

## 7. 已定、待定与后续组织能力

🟢 保留现有职责、版本保护、固定界面、独立Judge与分项计量；不因本次失败全面改架构。

🟡 三研究成员具体采集责任、无访谈深度、报告数量、经验权重／晋升、整任务累计硬预算继续待定。

🟡 真实组织共享、权限、后端接收与补传、全界面体验及六类业务的代表验收仍不完整；企业Git归档、知识库闭环、研发最终版本回流有待建设范围。

历史P0基础5/40仅是旧基础样本口径，不是当前代码完成率；一次正常结束也不能增加全产品绿色计数。
