## 3. A：开始前以真实事件为准

```text
讨论／准备   round.source=proposal；主Agent提出execute提案
   ↓ 提案受理 → 界面倒计时（程序显示）
已受理       点击开始或倒计时结束，task-admitted
   ↓
成员执行 → 独立检查 → 需要时返修 → 保存 → 结算回执
（每一步只由程序状态／回执表达）
```

1. execute正文只说明将产出什么、按什么范围；不写“几秒后开始/已开始/正在分析”。倒计时和开始由程序界面表达。
2. 提案工具返回拒绝时，正文不能已包含开始承诺；按错误修正重提，不向员工描述内部拒绝。
3. 成员执行、检查、返修、保存只依据Agent Status或交付回执转述；没有对应事件不预告。
4. 同步修正讨论阶段拒绝文案，不再暗示“会自动开始”。

程序状态计算（Agent Status、倒计时、主干）已按事件区分，本阶段只做回归保护，不重写界面。

## 4. B：结算后一次受控业务说明

```text
Judge结束 → 结算 → 回执状态确定（complete / saved_partial / failed / unknown）
   → 程序先发布回执：状态行由程序写，模型不改
   → 唤醒主Agent一次「交付说明」
        输入：本条回执、正式版/草稿/上一正式版入口、版本变化、未满足缺口
        工具：只读当前成果；派工、统计、检查、提案、写成果全部拒绝
        输出：成果要点、相对上一正式版的变化、限制与待定；入口用程序给的路径
   → 同一回执只说明一次；说明回合失败则只保留回执，不重试、不补话术
```

| 规则 | 说明 |
|---|---|
| 触发 | 只在回执进入确定状态后；`saving`不触发。未结算的自动通知继续走现有静音守卫（SR01不动） |
| 幂等 | 按回执ID记录是否已说明；重复通知、刷新、重启不重复说明 |
| 更正 | 出现`correction`回执（此前完成说明不准确）时，做一次更正说明，不删除旧说明 |
| 状态边界 | 状态以程序回执为准；非complete时说明需讲清草稿/旧版可看、缺什么，不写“已完成” |
| 混批 | 同批有真实员工消息时，员工问题照常回答（SR01-A行为保持），说明不吞员工输入 |
| 内容 | 简短，不复制正文；首版说明首版要点，更新轮说明变化；未知、推断和未验证写明 |
| 不做 | 不做关键词过滤代替状态边界，以免误伤并给出假安全感；模型表述是否准确属于最后统一的真实效果验收 |

依据：产品设计“主Agent负责说明成果，程序负责状态”（[设计与验收目标 §2](02-产品设计与验收目标.md)）。B1纯模板无法给出业务结论；B3（成员附摘要）改动成员合同和TeamRevision，留作阶段五耗时超标时的备选。

## 6. 验收：工程/静态本阶段完成，真实效果最后统一验

| 场景 | 预期 |
|---|---|
| execute提案被拒 | 提示词/拒绝文案不再要求预告开始；程序状态仍为讨论，未计running |
| complete回执 | 回执后恰有一次说明回合，公开文本可见；派工/统计/检查/提案/写成果被拒 |
| saved_partial / failed / unknown | 说明输入带实际状态与缺口；回执状态不被改写 |
| 未结算自动通知 | 仍不公开模型文本；SR01-A/B/C、T03、T05回归保持 |
| 重复通知/刷新/重启 | 同一回执不重复说明 |
| 更正回执 | 一次更正说明，旧说明与历史保留 |
| 说明回合失败 | 只保留回执，不重试，不改交付状态 |
| v2更新 | 说明输入含上一正式版与变化 |

合成替身只证明协议与守卫，不证明模型说得准。真实模型话术、浏览器显示、耗时由用户决定在阶段五完成后统一验收；本阶段收口写“工程/静态通过，真实效果待统一验收”。
