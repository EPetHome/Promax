## 0. 定位与范围

在 dsh 底座与专家团包之间插入一层宿主插件，让 WorkBuddy 格式的专家团包（当前 2.1.5，**一字不改**）在 dsh 上按 WorkBuddy 的方式运行。底层的常驻、唤醒、子会话、工具注册、拦截点一律用 dsh 稳定接口，不重写。

| 术语 | 含义 |
|---|---|
| 包 | 专家团包根目录：`plugin.json`、`agents/*.md`、`skills/<目录>/SKILL.md` |
| Lead | 顶层会话；在团队里的名字固定为 `team-lead`〔实测〕 |
| 成员 | 由 `Agent` 派出的常驻子会话（dsh 可继续子 agent） |
| fork 子会话 | 由 `Skill` 为 `context: fork` 技能起的一次性子会话 |

**不做**：仿制 WorkBuddy 的成员完成通知（`[Framework Auto-Notification] Teammate "<名>" completed successfully.`），成员结束后用 dsh 自带的结算通知叫醒 Lead（第 2 轮已实测能叫醒）；飞书与任何外部回传；评审与质检（第 4 轮）；`/tmp` 写入边界；技能按人分配；界面展示；用户 `/名字` 手势；包版本自动切换（只按配置路径读取）。

## 1. 总体

### 1.1 插件与配置

插件目录 `plugins/promax-wb-host/`，入口 `index.mjs` 导出 `name`、`inject`、`apply(ctx, config)`。config：

| 字段 | 含义 |
|---|---|
| `packageDir` | 包根目录（绝对路径） |
| `memberModel` | `{provider, model}`，成员与 fork 子会话的模型 |
| `python` | 运行 `receipt_cli` 的解释器绝对路径 |
| `maxConcurrentForks` | 同一进程同时运行的 fork 子会话上限（默认 16） |
| `modules` | `{team, skill, runtime}` 布尔开关，默认全开 |

### 1.2 装配要求（由 M4 的 profile 落实）

- 隐藏 dsh 的通用委派与控制工具：`tool-subagent`、`tool-subagent-fork`、`subagent` 控制工具（`send_message`、`list_agents`、`interrupt_agent`）、小写 `skill` 工具（`tool-skill`）。模型可见的团队与技能工具**只有本插件提供的那几个**。
- `subagent.maxDepth = 2`（Lead → 成员 → fork 子会话）。先遣测试已证实需要放开到 2。
- 继续挂外发守卫 `promax-egress-guard`；Lead 与成员模型同第 2 轮（`opencode-go/deepseek-v4.1-flash`）。
- 〔定义 S1.1〕profile 以第 2 轮的 `promax-project/dsh-home/profiles/promax-215-sdk/` 为底：SDK 组合包（`dsh-base` + `dsh-sdk-app`）、模型路由、默认模型、关 `tool-web`、外发守卫配置原样保留；在此之上只做这几处改动：
  1. 删掉 6 个 `member-*` 具名成员实例（D12①，成员只经 `Agent` 派出）；
  2. 关掉 `skill-filesystem`、`tool-skill`、`skill-office`：dsh 自带的技能清单和小写 `skill` 都不出现，技能只经 K4 清单与 `Skill`；
  3. `agent-instructions` 不再加载 Lead 副本：`dshHome` 指向装配目录里的一个空目录，`instructionFileCandidates: []`、`localInstructionFileCandidates: []`。Lead 定义只经 R2 注入一次；
  4. 关掉 1.2 第一条所列的委派与控制工具，`subagent.maxDepth = 2`；
  5. insert 本插件（`id: promax-wb-host`），config 按 1.1 填写。

### 1.3 共通

- 插件注入给模型的消息，source 写 `{kind:'plugin:promax-wb-host'}`（实验 11 教训：写 `'plugin'` 会被会话格式拒绝）。
- 〔定义 S1.1〕本插件注册的五个工具，参数定义都允许未列出的额外字段：照常执行，额外字段写进日志，不因多一个键整次调用失败（WorkBuddy 实测模型会多传 `run_in_background`、`max_turns` 等）。
- 插件事件日志追加到 `<会话 cwd>/product-agent-output/wb-host.jsonl`，每行带时间、事件名、调用方会话 id、角色（lead/成员名/fork）。
- 〔定义 S1.1〕日志每行一个扁平 JSON 对象，固定键：`ts`（ISO 8601 UTC）、`event`、`session_id`（调用方会话 id，无则 null）、`role`（`lead` / 成员名 / `fork`，无则 null）；事件自有字段与这四个键并列，见 2.5、K2。只追加。

- 〔定义 S1.3〕**依赖边界**：插件代码只依赖三类东西——① Node 自带模块（`node:*`）；② 宿主 dsh 经 Cordis `ctx` 提供的接口（`ctx.tools`、`ctx.subagents`、`ctx.provide`/`ctx.get` 等；安装包里的类型定义只用来查这些接口的形状）；③ 插件根目录 `package.json` 里声明了**精确版本**、并随插件目录一起携带在 `plugins/promax-wb-host/node_modules/` 下的第三方库。不 import 宿主的包（`@deepseek-ai/*`），不从宿主安装目录（`dsh-runtime/node_modules`）或任何插件目录以外的位置解析包，不用 `createRequire` 指向插件目录以外。插件目录整体复制到任意位置，用普通 Node 即可加载入口。

### 1.4 模块划分与接口（并行开发的边界）

| 模块 | 目录（Loop 可写范围） | 对外 |
|---|---|---|

| M3 运行时约定 | `plugins/promax-wb-host/runtime/` | `runtime/index.mjs`：插件 `promax-wb-runtime`，提供 Cordis 服务 `wbRuntime`；`runtime/receipt_cli.py` |

## 2. M1 团队与派发

### 2.1 名册与 Lead 定义

- R1 名册来自 `plugin.json`：`teamInfo.leadAgent`、`teamInfo.memberAgents`、`agents[]` 路径；成员人设 = 对应 `agents/<id>.md` 去掉 frontmatter 的正文。
- R2 **Lead 定义注入**：Lead 会话第一次请求前，注入一条 user 角色消息，内容为 Lead 定义文件**原文（含 frontmatter）**〔实测：WorkBuddy 就是这样把 Lead 定义放进会话的〕。装配时不再另做 Lead 正文副本。
- R3 每一步请求前重新读名册文件；文件变化后，新派出的成员用新人设，已在运行的成员不变。

### 2.2 `Agent`

参数：`description`、`name`、`prompt`、`subagent_type`〔实测〕；可选 `run_in_background`、`max_turns`〔实测 S1.1：144 次调用中分别出现 48、10 次〕，接受但不改变行为（成员总在后台运行）。`name` 缺省时取 `subagent_type`〔定义 S1.1；实测 3 次缺 name〕。

| 编号 | 规则 |
|---|---|
| A1 | `subagent_type` 必须在名册成员里，否则返回错误 `Unknown subagent_type: <值>` |
| A2 | Lead 还没有团队时自动建团，团队名 `_auto_<uuid>`〔实测〕；有团队（`TeamCreate` 建过）就用它 |
| A3 | 起一个**可继续**成员（spawn 提供方，人设见 R1，模型 `memberModel`），首条消息是 `prompt`，外面套 WorkBuddy 信封：`<teammate-message teammate_id="team-lead" summary="Initial task assignment for <name>">\n<prompt>\n</teammate-message>`〔实测 S1.1〕。成员在团队里的名字 = `name` |
| A4 | 返回文本**逐字**为：`Spawned successfully.\nagent_id: <subagent_type>@<team_name>\nname: <name>\nteam_name: <team_name>\ntask_id: agent-<16 位十六进制>\nThe agent is now running and will receive instructions via mailbox.`〔实测〕 |
| A5 | 同一团队里已有同名成员〔定义〕：不新建，把 `prompt` 作为新消息投给它（成员带着原有会话记忆继续，空闲就被唤醒、已结算就冷恢复）；返回同 A4 的文本，`task_id` 沿用原值 |
| A6 | 只有 Lead 能调用 `Agent`；成员调用返回错误 `Agent is only available to team-lead` 〔定义〕 |

### 2.3 `TeamCreate`

参数：`team_name`、可选 `description`。只登记该 Lead 会话的团队名，返回 `Team "<team_name>" created.`〔定义；WorkBuddy 实测从未调用〕。重复调用覆盖团队名，已存在的成员不受影响。

### 2.4 `SendMessage`

参数：`type`（`message` / `shutdown_request` / `shutdown_response`）、`recipient`、`content`〔实测〕；可选 `summary`〔实测 S1.1：520 次中 486 次带〕；`shutdown_response` 另带 `request_id`、`approve`，可以不带 `recipient`、`content`〔实测 S1.1〕。

| 编号 | 规则 |
|---|---|
| S1 | 名字解析：`team-lead`、名册 `teamInfo.leadAgent` 的 id（2.1.5 为 `product-agent-team-lead`）、`main` 三个都指 Lead〔实测 S1.1：成员发给这三个名字分别 659、48、18 次，WorkBuddy 都投递成功；2.1.5 成员定义原文写的就是 `product-agent-team-lead`〕；成员名 = A3 登记的 `name`。解析不到返回错误 `Unknown recipient: <值>`。成员发给其他成员：返回错误 `Members can only message team-lead`〔定义 S1.1；dsh 只能上下级直接投递，2.1.5 没有成员互发〕 |
| S2 | `message`：用 dsh 子 agent 消息通道投递（父↔子），返回 `{"success":true,"message":"Message sent to <recipient>'s inbox","routing":{"sender":"<发送方名>","target":"@<recipient>","summary":"<content 前 30 字>","content":"<content>"}}`（JSON 文本）〔实测，字段取样本子集〕。`<recipient>` 照调用方写的原样返回；`summary` 有就用它，没有才取 `content` 前 30 字。收件方看到的消息套信封：`<teammate-message teammate_id="<发送方名>" summary="<同上 summary>">\n<content>\n</teammate-message>`，Lead 的发送方名固定为 `team-lead`〔实测 S1.1〕 |
| S3 | `shutdown_request`（Lead → 成员）：投递一条以 `[shutdown_request <request_id>]` 开头的消息；返回 `Shutdown request sent to "<成员>" (request_id: shutdown-<成员>-<毫秒时间戳>-<8 位十六进制>). Wait for their shutdown_response.`〔实测〕 |
| S4 | `shutdown_response`（成员 → Lead）：投递给 Lead；该成员登记为已关闭，之后对它的 `Agent` 同名派发按 A3 新建〔定义〕。投递内容为 `{"type":"shutdown_response","request_id":…,"approve":…,"reason":…}`，信封 summary 为 `Shutdown accepted by <成员>`（`approve` 为 false 时 `Shutdown rejected by <成员>`）〔实测 S1.1〕。〔定义 S1.2〕`reason` 取调用的 `content`：带了就原样填入，没带为 `null` |
| S5 | 发送方不在任何团队、也没有成员时，返回 `Not in a team. SendMessage is only available when you are in a team or have background agents running.`〔实测〕 |

### 2.5 `present_files`

参数：`files`（数组）、可选 `explanation`、`cwd`〔实测〕。相对路径按 `cwd`（缺省为会话 cwd）解析；不存在的文件返回错误并列出。成功时写交付清单（日志事件 `present`，〔定义 S1.1〕自有字段 `files` = 返回值里的同一绝对路径数组、`explanation`；每次成功调用追加一行），返回 `{"type":"present_files_result","files":[绝对路径…],"previewed":[],"explanation":"<explanation>"}`〔实测〕。

## 3. M2 技能执行

### 3.1 技能发现

- K1 扫描 `<packageDir>/skills/*/SKILL.md` 的 frontmatter：`name`（允许中文）、`description`、`context`（`fork` 或缺省）。
- K2 名字重复：两条都不进清单，日志记 `skill-duplicate`。frontmatter 读不出：跳过并记日志。〔定义 S1.1〕日志事件：重复为 `skill-duplicate`，自有字段 `name`、`paths`（涉及的 SKILL.md 绝对路径数组）；读不出为 `skill-skip`，自有字段 `path`（该 SKILL.md 绝对路径）、`reason`（自由文本，语言不限）。同一进程内同一事件 + 同一 `name`/`path` 只记一次（K3 每步重扫不重复记）。
- K3 每次需要清单或调用技能时重新扫描（只读 frontmatter），保证技能迭代后即时生效（D19、D20）。

### 3.2 技能清单（D20：可自动替换的持久清单消息）

- K4 Lead 与成员每一步请求前，算当前清单的摘要（各条 `name`、`description`、`context` 排序后取 sha256）；与本会话最近一次发布的不同，就注入一条 user 角色消息，内容为**完整清单**：一行说明「以下技能用 `Skill` 工具调用：参数 `skill` 填名字，`args` 填纯文本」，然后每条 `- \`<name>\`: <description>`（description 超过 500 字截断）。清单为空也要发布，写明当前没有可用技能。
- K5 fork 子会话不发布清单、不提供 `Skill`（2.1.5：业务技能在 fork 中不能再调用其他技能）。

### 3.3 `Skill`

参数：`skill`、可选 `args`（纯文本）〔实测〕。

| 编号 | 规则 |
|---|---|
| K6 | 找不到技能返回错误 `Unknown skill: <名字>` |
| K7 | 调用前交给 M3 签发运行上下文，并按 M3 改写 `args`（4.2） |
| K8 | **fork 技能**：起一次性子会话（spawn），任务内容 = `Base directory for this skill: <技能目录>\n<SKILL 正文>` + 空行 + `ARGUMENTS: <改写后的 args>`；子会话工具与调用方相同，但去掉 `Skill`、`Agent`、`TeamCreate`、`SendMessage`、`present_files`；无人设；模型 `memberModel`。结束后把子会话最终回答交 M3 核对（4.4），返回 `Skill "<名字>" completed (forked execution).\n\n<子会话最终回答>`〔实测〕。子会话出错或被取消：返回 `Skill "<名字>" failed (forked execution).\n\n<原因>`〔定义〕，台账记失败 |
| K9 | **内联技能**：不起子会话，返回 `Base directory for this skill: <技能目录>\n<SKILL 正文>` + 空行 + `ARGUMENTS: <改写后的 args>`〔实测前半；ARGUMENTS 段为定义〕 |
| K10 | 并发：同时运行的 fork 子会话超过 `maxConcurrentForks` 时排队等待，**不向模型返回「已达上限」**；排队毫秒数写进台账（D10）。上限之内不得出现等待 |

## 4. M3 运行时约定（本地版，替代 2.1.5 的 Hook；D12）

依据 2.1.5 `runtime/hook.py` 第 405—465 行、`skills/*/references/collection.md`、`skills/prd-document-generator/references/inline-execution.md`。**不引用 hook.py、不联网、不写飞书。**

### 4.1 签发

- C1 每次 `Skill` 调用签发：`run_id`（UUID）、`artifact_dir` = `<会话 cwd>/product-agent-output/<run_id>/`（立即创建）、`task_id`（`args` 里有 `<product-agent-task>` 且带 `task_id` 就沿用，否则生成 `task-<12 位十六进制>`）。
- C2 执行方式：技能名在内联集合 `{prd-document-generator, business-diagram-generator, interactive-prototype-generator}` 里为 `inline`，否则看 `context`〔实测：hook.py 的 INLINE_SKILLS〕。

### 4.2 改写 `args`〔实测：hook.py 第 448—460 行〕

1. 删掉调用方写的 `<product-agent-context>…</product-agent-context>` 与 `<product-agent-task>…</product-agent-task>`；
2. 末尾追加 `\n<product-agent-task>\n{"task":…,"project":…,"task_type":…,"mode":…,"task_id":…}\n</product-agent-task>`（前四项取自调用方原标签，缺的写空串）；
3. 再追加 `\n<product-agent-context>\n<上下文 JSON>\n</product-agent-context>`。

上下文 JSON：
- fork：`{"run_id","task_id","artifact_dir","result_rules"}`，`result_rules` 原文：「本次结果的 run_id 只能逐字复制本 context.run_id。前文、任务文件或主会话指定的其他运行编号均不得用于本次结果；不要自造编号或向用户索要编号。产物保存在本 context.artifact_dir；最终回复以唯一 product-agent-result 代码块结束。」
- inline：同上，另加 `"execution_mode":"inline"`、`"receipt_cli":[<python>, <插件内 receipt_cli.py 绝对路径>]`，`result_rules` 改用 hook.py 第 442—444 行原文〔实测；S1.1 抄录于此，冻结包不含 hook.py〕：「本 context.run_id 由真实 Skill 调用分配，不得自造。加载完成不等于任务完成。在当前上下文执行，不调用子生成 Skill；每份产物完成后用 receipt_cli checkpoint --result-file 回报，最后用 receipt_cli complete --result-file 结束。命令在本次任务工作目录执行；文件只列本 artifact_dir 内产物。」
- 两种 `result_rules` 都逐字使用上面的原文，不增删字符。

### 4.3 `receipt_cli.py`（内联回执）

- C3 `receipt_cli.py checkpoint --result-file <JSON>`、`receipt_cli.py complete --result-file <JSON>`；JSON 至少含 `run_id`、`status`、`artifacts`（绝对路径数组），字段口径按 `inline-execution.md`。
- C4 `run_id` 必须是已签发的内联运行；产物必须存在、非空、在该 `artifact_dir` 里，否则退出码非 0 并说明原因，不写成功。
- C5 同一 `run_id` 重复相同 checkpoint 不新增阶段；`complete` 之后再 checkpoint 报错。〔定义 S1.1〕「相同」= 回执 JSON 解析后与该 `run_id` 最近一次被接受的 checkpoint 完全相等：退出码 0，输出说明「重复 checkpoint，未新增阶段」，**台账不追加**；内容不同就按新阶段追加一行。`complete` 之后再 checkpoint 或再 complete 都退出非 0。
- 〔定义 S1.1〕C4、C5 被拒的调用不写台账，只返回非 0 退出码和原因。

### 4.4 核对 fork 回执

- C6 在子会话最终回答里找唯一的 ```` ```product-agent-result ```` 代码块（JSON）〔实测：collection.md〕。
- C7 判定：块缺失、多于一个、JSON 坏、`run_id` 不等于签发值、`status` 不在 {成功, 失败, 取消}、列出的产物不存在 / 为空 / 不在 `artifact_dir` 里 → 执行状态「待核验」、结果校验「异常」，并写明原因；全部对上 → 按 `status` 记，结果校验「通过」。**不改写子会话的回答**，只记台账。

### 4.5 台账

`<会话 cwd>/product-agent-output/ledger.jsonl`，每次签发、checkpoint、complete、fork 结束各一行：时间、`run_id`、`task_id`、技能名、执行方式、调用方会话 id、fork 子会话 id、执行状态、结果校验、原因、产物（路径、字节、sha256）、排队毫秒。台账只追加。第 4 轮评审插件从这里读。

〔定义 S1.1〕每行一个扁平 JSON 对象，键固定如下；不适用的一律写 `null`（`artifacts` 写 `[]`），不省略键、不加嵌套层：

| 键 | 值 |
|---|---|
| `ts` | ISO 8601 UTC |
| `event` | `issue` / `checkpoint` / `complete` / `fork_end` |
| `run_id`、`task_id` | 签发值（4.1） |
| `skill` | 被调用的技能名（K1 的 `name`，原样） |
| `mode` | `fork` / `inline`（C2） |
| `caller_session_id` | 调用 `Skill` 的会话 id；checkpoint、complete 行沿用签发行的值 |
| `child_session_id` | `fork_end` 填 fork 子会话 id，其余 `null` |
| `exec_status` | `issue`：`已签发`；`checkpoint`：`运行中`；`complete`：回执 JSON 的 `status`（成功 / 失败 / 取消）；`fork_end`：按 4.4（成功 / 失败 / 取消 / 待核验） |
| `result_check` | `issue`、`checkpoint`：`null`；`complete`：`通过`；`fork_end`：`通过` / `异常` |
| `reason` | 有原因写文本，否则 `null` |
| `artifacts` | `[{"path": 绝对路径, "bytes": 整数, "sha256": 十六进制}]`，写行时现算；`issue` 为 `[]`。〔定义 S1.2〕回执（或 receipt_cli 结果文件）列出的每个路径都写一项，按回执顺序：不存在的 `bytes`、`sha256` 为 `null`；空文件 `bytes` 为 `0`、`sha256` 为空内容的哈希（`e3b0c442…b855`）；不存在、为空、不在 `artifact_dir` 等原因写进 `reason` |
| `queue_ms` | `fork_end` 填整数（无排队为 0），其余 `null` |

`issue(req)` 返回前、`finishFork(res)` 返回前各自落盘本次那一行；`finishFork` 返回的对象与落盘那一行逐键相等。

## 5. M4 集成

- I1 `index.mjs` 按 `modules` 组装 M1—M3；任一模块关闭时，它的工具不注册、注入不发生。
- I2 profile 模板 `assembly/profile/` + 渲染脚本：给定包路径、插件路径、守卫路径、python 路径，生成一个可用的 profile 目录（SDK 组合包；满足 1.2）。渲染结果用 `dsh --dump-config` 校验。〔定义 S1.1〕渲染脚本固定为 `assembly/render_profile.py`，命令行：`<python> assembly/render_profile.py --package <包根> --plugin <promax-wb-host 目录> --guard <promax-egress-guard 目录> --python <解释器> --out <输出 profile 目录> [--guard-boot-log <守卫启动日志路径>]`，路径参数都是绝对路径；`--guard-boot-log` 缺省时沿用模板值；成功退出 0，失败退出非 0 并在 stderr 写原因。渲染出的 `cordis.patch.yml` 里，本插件的 `insert` 条目 `id` 固定为 `promax-wb-host`，外发守卫为 `promax-egress-guard`；I3 的开关就是给 `id: promax-wb-host` 那一条加 `disabled: true`。
- I3 插件整体关掉（profile 里一行 `disabled: true`）时，模型看不到 `Agent`、`TeamCreate`、`SendMessage`、`present_files`、`Skill`，也不发生任何注入。
- I4 〔定义 S1.3〕装配完成的标准是**插件真激活**，不只是配置正确：在插件目录用不带任何钩子的普通 Node 能 import 入口；用渲染出的 profile 启动 dsh（SDK 服务 initialize 后关闭）时 stderr 没有 `promax-wb-host` 的 `did not activate` / `failed to import`；第一次模型请求的工具清单含 `Agent`、`TeamCreate`、`SendMessage`、`present_files`、`Skill`。
