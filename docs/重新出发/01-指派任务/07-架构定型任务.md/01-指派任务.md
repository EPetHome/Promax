## 3. 架构约定（4 个接口位）

```text
以后：界面 / 后端 / Promate / 飞书 / 公司文档
        │
  ① 调用入口   界面和后端怎么调用 agent        dsh 自带 sdk、server、web（现在是命令行 headless）
  ② 模型路由   每个成员用哪个模型               dsh 模型路由 + 成员 agentOptions（provider、model、reasoningEffort、maxTokens）
  ③ 成果契约   产出什么文件、什么格式           版本文件 + 保存回执 + 检查台账（加版本号、写成文档）
  ④ 外部服务   公司系统怎么接进来               dsh 自带 mcp-client、identity；只通过 MCP 或 dsh 插件
        │
Agent 核心：dsh + 专家团（规则、角色卡、技能）+ Judge（程序工具）
```

| 接口位 | 本任务做什么 | 约束 |
|---|---|---|
| ② 模型路由 | 「成员 → 模型路由」集中在一张配置表；以后公司模型作为一条路由接入，只改表不改成员 | 旧版做法可参考：`old-version/promax-ui/packages/promax-bundle/src/company-connection.ts`（把公司模型注册成 dsh 路由） |
| ③ 成果契约 | 给保存回执、检查台账加 `schema_version`，写一份格式说明 | 以后后端只收产出；可评估对接旧后端的成果版本、检查报告、缺陷接口（`old-version/promax-end/contracts/openapi.json`） |
| ① 调用入口 | 不做 | 界面和后端通过 dsh 的 sdk、server 调用，不自写调度层 |
| ④ 外部服务 | 不做 | 公司服务不写死在 agent 里 |

🔴 **红线**：以后接后端时，后端只接收 agent 的产出，**不参与调度**（旧版自造协议和 dsh 原生调度冲突，导致 RE-13 卡死）。
