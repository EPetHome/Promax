### 3. 哪些行为算一次业务返修 [主线必需｜NJ]

1. 同一成果版本、同一检查组中，**Judge 的 `REVISION_REQUIRED` 结论已被程序接受 → 写手据此改稿 → 再次正式检查**，构成一次业务返修；最多一次。保存前后的回执要反映同一个真实事件。
2. 重复预检、查看输出、修 Judge 草稿格式、提交被拒后重交、作者自查，都不算业务返修，也不能占掉这一次额度。
3. 同一内容重复预检不新增返修轮；内容在尚未形成有效检查结论前改变，可以更新预检快照。旧快照不能用于接受新内容；不能为了恢复流程关闭 SHA 校验。
4. 写手自查不能写入正式检查流水、创建正式轮次或占用正式检查额度。若复用同一检查程序，应有无正式副作用的自查方式；不能仅用一句“不要调用”掩盖程序仍会误计的事实。
5. 判定依据是持久保存的实际事件和对应内容版本，不用“预检调用次数减一”、现存目录数或模型自报次数替代。
6. 删除检查组、换草稿名、换 Judge、重开会话、重复保存同一内容，都不能获得新的业务返修额度。
7. 只复查已有正式版本不自动等于返修；有真实新版材料的 v2 按新版本处理，并保留 v1。不能把上游成果误当自己的上一版来开启新周期。

### 4. 草稿拒收与格式修复 [主线必需｜NJ]

- 每个检查组的同一待提交草稿有两种独立额度：**JSON 语法修复最多 1 次；非语法的草稿拒收修改最多 1 次**。因此从首次提交起，最多初稿加两次修改，不能无限交替错误类型。
- 只有 JSON 语法错误使用格式额度。缺少草稿、字段缺失、引文不逐字、目标错误、快照不一致等不能伪装成 JSON 语法错误；被拒的全部尝试都保留原因。
- 某类额度耗尽后再次发生同类拒收，即停止这份草稿，不借另一类余额继续。例：语法错 → 修格式后引文错 → 修引文后接受，可完成；语法错 → 修后仍语法错，应停止。
- 修格式只修序列化表达，不改变 `quote` 解码后的原句、检查结论和实质问题。引文仍由现有逐字校验核实；格式修复后引文变化不能被豁免。
- 草稿始终由 Judge 写；Lead 只转交程序错误和草稿位置，不手改、不写脚本代修。更换 Judge、改变文件名或删除台账不重置额度。
- 程序输出须区分业务返修次数、语法拒收与修复次数、其他草稿拒收与修复次数、剩余额度及停止原因；保留旧字段含义，不让不同类型合成一个误导性数字。
