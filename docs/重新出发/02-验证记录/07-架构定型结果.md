**据此判断（有效结论）**：

1. 成员单独配模型用路线 A 可以实现：只改配置，不改 dsh 源码、不写插件；**路线 B 不再需要**。
2. 现有 opencode-go 密钥能调用 v4-pro。
3. 前台调用的成员是一次性子会话。想要「下一轮找回同一成员」，只能用后台可续跑方式；而命令行模式下，后台成员能否在一轮内等到结果还没有验证。所以目前可行的方案是**每轮新建成员，靠文件（台账、变更清单、版本）接续**，只复查场景已经证明可行。
4. 成员工具的 `maxDepth` 必须是 1。

**不能推出**：路线 A 更快（上一轮 559 秒主要是网关尖峰，去掉约 274 秒，与本轮 300 秒接近；n=1）；v4-pro 做 Judge 更差（模型和环境同时变了，n=1）；写手在 v2 更新时能否靠文件接续（没跑）；成本高低（没有单价）。

**对 pi 报告的核对**：pi 的事实描述基本准确，并且发现了 Claude 漏掉的三点（一次性子会话、写手超窗、交付说明未披露）。有两处说过头：「效率改善」没有提上一轮的尖峰；「可靠性未见退化」没有把写手报错算进去。pi 说「模型证据只能靠同会话请求头覆盖」偏保守，其实流记录里有逐次响应的模型名。

**Claude 的规格错误**（写进任务书，1b 不再犯）：`maxDepth: 0`（应为 1）；「前台等待后仍可续用」（前台是一次性的）；「每次请求前有 request/header」（每个会话只有 1—3 条）。
