# 问题原因与三条修复主线

📍 **核心原因：统计、正文修改、评审、正式保存和最终回复分别在工作，但关键交接没有全部由一致的事实约束。**本页保留我们“为什么会这样”的详细解释；问题状态只在[问题总表](01-问题总表与排队关系.md)维护。

日期：2026-09-23。标记：📎外部运行证据；🟢本地静态代码依据；🟡尚待区分的原因；📍候选改法，未实施。

## 1. 数据替换与局部修改：哪一层做对了

📎 E01显示v2只把T0076的rating由3改1，其余319条未变。保留v1、v2和旧报告三个来源，是为了当前计算、差异对照与修改基线，不是把两个JSON拼成640条。

🟢 `rating-facts.ts`先加载当前source_id，统计返回当前版本；previous_source_id用于按唯一record_id比较全部字段值，没有把两个数组合并统计。

```text
当前v2 → 当前评分事实
旧v1  → 与v2作差异对照
旧报告 → 预置为修改基线 → 成员更新必要位置
```

正文更新了1星、3星、低星比例、T0076例子、相关建议依据及附录。这说明成员本次基本遵循影响范围；不证明程序已经能自动保证任意语义修改范围，也不证明正式提交成功。

局部修改还保留了旧稿中被Judge改错的句子。**保留未变内容与旧稿全部正确，是两种不同性质。**后续仍要处理有事实冲突的旧问题，不机械继承旧语义PASS。

## 2. Judge为什么把正确内容改错又放行

📎 原始事实：T0301—T0320有20个编号，这20条评分都无效；T0300有效，但不在该范围内。原稿正确，Judge误称范围内21条且含T0300，成员据此写出“并非该编号范围整段无效”，后续又verified／PASS。

```text
Judge提出结构合法但事实错误的问题
        ↓
主Agent安排返修，成员按问题修改
        ↓
复查确认“T0300有效、20条无效在范围内”
        ↓
却放行“这个范围并非全部无效”这一不同命题
```

🟢 当前程序保护评审请求、输入版本、文件哈希、合法字段和必回查覆盖；这些检查不能自行证明自由文本意见的事实正确。现有返修简报强调按主Agent安排处理问题，但证据冲突时的异议／核对路径尚未充分落实。

🟡 为什么模型这一次读错范围，现有材料不能唯一归因于上下文长、注意力或模型能力。可确定的是错误意见进入了返修，复查又没有纠正其逻辑前提。同Judge责任连续性有价值，但历史verified不能作为独立真值。

📍 建议：对可计算的数值／集合断言绑定明确事实；评审意见若与事实冲突，先由程序核对可确定部分，再由原Judge重新判断。成员可提出有证据的异议，但不能自行忽略Judge或让主Agent自评放行。解决不了的争议保持待核；保留本例为独立反例。

## 3. 草稿存在，正式保存为什么失败

草稿快照用于可读、算哈希和检查；正式版本库另负责版本关系与当前指针。因此草稿存在和Judge PASS都不等于正式保存成功。

### 3.1 标题契约不一致

📎 本次anchor.value为`## 一、评分分布与数据质量`，旧新稿标题均存在且唯一。

🟢 [anchorRange](../../../old-version/promax-ui/packages/promax-bundle/src/artifact-operations.ts:132)将Markdown标题解析成去掉井号的文字，再和原传入值直接比较：

```text
解析值：一、评分分布与数据质量
传入值：## 一、评分分布与数据质量
直接比较 → 不相等 → 报“章节锚点不存在或不唯一”
```

这与本次错误吻合，属于静态判断，没有运行复现。错误文案不能被直接解释为“文件真的没有该标题”。

### 3.2 为什么直到最后才发现

直接成果编辑入口会先调用anchorRange；主Agent结构化提案路径主要校验字段结构和基线哈希，没有同等提前校验锚点能否在旧稿解析。两条入口的前置检查不一致，使可提前发现的问题拖到评审后。

🟢 [settleTaskRun](../../../old-version/promax-ui/packages/promax-bundle/src/index.ts:7305)的顺序是读取基线／新稿→计算锚点外差异→正式commit→写运行控制终态。此次锚点检查抛错会挡住后续提交。

### 3.3 现有存储已经能提交完整文件

🟢 [ContentObjectStore.commit](../../../old-version/promax-end/packages/promax-report/src/content-store.ts:318)读取完整文件字节、检查基线哈希和同任务提交身份、更新版本索引。不是只支持字符串章节替换。

因此外部提出“跨章节按base_sha提交完整新版本”的方向可复用现有能力；先修编辑契约和范围表达，不应在未查源码前另造一套全文提交系统。现有outsideAnchorChanges只是对前后范围变化做记录，也不等于已实现任意语义影响分析。

### 3.4 为什么最后还能说完成

🟢 程序已有delivery_saved=false、失败进度与共享完成计算中的“成果版本尚未保存”缺口；[coordinatorContext](../../../old-version/promax-ui/packages/promax-bundle/src/index.ts:7528)能把completion、成果状态及last_progress提供给主Agent。

📎 E03却显示15:24:03保存失败后，15:24:21仍回复“报告已更新完成”。

🟢 2026-09-23新增原始会话读取已进一步区分：seq19821首次完成声明沿用的header seq16927仍是“检查中”；seq19826的新header随后明确包含保存失败／部分完成，但seq19858只让用户看上面的报告，没有纠正。证据支持“首次状态滞后＋后续未纠正”两段问题；不把模型内部原因或精确异步交错写成已经运行证明。详见[唯一P0定位](../../../old-version/docs/核查证据/证据质量与计分判定-20260922/RESULTS.md#p0-delivery-diagnosis-20260923)。

此外，程序先把round置ended，提交成功后才写run-control终态，中间抛错可留下ended与running并存。这个顺序能解释字段差异，但不能据此宣称模型仍在执行。需要按各自契约判断并形成一致的用户状态。

### 3.5 本次P0归因已收敛到哪几层

2026-09-23进一步只读核对了本地原始`工作关联.yml`、冻结修改源、新稿和DSH生命周期代码：

| 层次 | 归因 | 证据与确定程度 |
|---|---|---|
| 保存失败的直接原因 | 传入带`##`的整行标题，解析器却用去掉井号的标题文字直接比较 | 原始关联值、基线SHA及第17行标题与解析代码吻合；不是标题缺失或重复，也未执行新复现 |
| 问题被拖到最后的原因 | 主Agent结构化修改提案校验基线哈希，没有统一执行锚点有效性预检 | `validateProposal`静态可见；正式提交前才进入outsideAnchorChanges |
| 首次回复使用旧状态的机制 | DSH先通知父Agent成员结束，再emit子成员end；Promax在异步end监听器内提交，emit不等待其Promise | 原生`continuation.ts:1434—1440`及`lifecycle.ts:112—116`；归档header与回复时序相符，精确await交错尚未运行复现 |
| 失败未被纠正的机制 | 失败虽进入后一请求，最终自然语言仍未纠正；round已ended，后续completeWorkExecution直接返回 | 原始seq19826/19858及静态完成链；共享partial状态已有，但不能保证被正确表达 |

归因主体是Promax的契约／集成和交付状态消费约束，同时存在主Agent错误完成表达及后续未纠正的可观察行为。DSH的非阻塞通知本身不能直接判为缺陷；问题在于Promax依赖其异步监听器执行必须在交付前确定结果的业务提交，却没有建立对应等待和最终说明约束。不是将“模型不认真”作为唯一原因，也没有证据归咎统计器、网络、磁盘故障或R32。

正式保存失败与误报完成是两个独立问题：修好标题只消除本次触发；仍需保证其它失败／未知结果下不产生或保留错误完成说明。详细归因及原始文件身份见[唯一RESULTS归因补充](../../../old-version/docs/核查证据/证据质量与计分判定-20260922/RESULTS.md#p0-attribution-20260923)。

## 4. 凭证与问题身份：为什么看起来严格仍会错

### 4.1 算对一个数，不等于证明整句结论

📎 CNL-009说文本去重后19种，CNL-010说三个字段一致；两者却都挂rating_total=320的matched凭证。这两个结论在样本中恰好成立，但凭证没有证明它们。

| 断言 | 必须对应的事实 | rating_total=320能否证明 |
|---|---|---|
| 总记录320 | 总记录数 | 能 |
| 不同文本19种 | distinct(text) | 不能 |
| 日期字段全一致 | date字段一致性 | 不能 |
| 编号范围全部无效 | 该范围记录集合与有效性结果 | 不能仅凭总行数证明 |

🟢 数值复算只执行声明规格；随后依据汇总把存在matched的数值项计为某类可用证据。Judge仍需要核对支持关系。当前固定指标覆盖与断言的具体对应不够明确，造成“某项计算正确”被扩大理解为“整条有证据”。

📎 json:all的限制导致一些全量结论被拒，后续挂上rating_total便得到接受。协议可能促使模型寻找可通过的规格，这只是对行为序列的解释，不认定模型有意欺骗。

### 4.2 问题ID为什么会串

🟢 [acceptCheckResult](../../../old-version/promax-ui/packages/promax-bundle/src/work-store.ts:780)按成果组＋模型提交的issue.id寻找旧记录，找到后覆盖当前内容。E06中的同一QJ-R1-01因此先后承载文本归类与数值凭证缺口，复查历史混在一起。

📍 内部身份应由程序维护；新问题、复查、重开分别引用明确身份。仅加一个UUID不够，还要设计模型怎样引用旧问题、展示标签怎样映射，以及旧记录如何兼容，不能清洗历史来伪造一致。

## 5. 为什么20多分钟才PASS

📎 新统计只有2次；更新正文到PASS约19分57秒。两轮更新评审正文哈希一样，主要在补凭证，不能再笼统说成员反复重新算数据。

### 5.1 模型仍在搬运程序已经知道的字段

统计工具已经返回正确numeric_specs，但成员还需在长回执中复制、拼装结论原文、正文定位、来源范围、规则ID和规格。它们与实际文件不完全匹配就被拒；修正又带来新的请求与上下文。

### 5.2 错误诊断没有说清字段

🟢 `matched`同时比较结果、分子和分母；错误只打印结果。本次计数分母填320，实际应为1，就出现“结果20与可复算20不一致”。应返回具体哪个字段错，不能把它描述成计算器认为20不等于20。

### 5.3 机械缺项过晚进入Judge

更新首轮Judge发现3星74、低星76/300缺凭证，成员补登，再开复查。固定评分项能否完整绑定，可以在派Judge前由程序检查；保留必要证据不意味着必须用一轮模型发现机械缺项。

### 5.4 会话连续性与历史负担混在一起

181次模型请求、约1477万累计输入说明上下文很重，但不能据此把全部请求列为浪费。当前工具结果限量已存在；[摘要触发](../../../old-version/promax-ui/packages/promax-bundle/src/context-budget.ts:89)同时要求超过soft且limit非空。C/R未知时limit=null，设计中的阈值不等于实际已有硬限制或自动摘要。

需要核对系统提示、工具schema、历史与当前证据的组成及估算误差。保留Judge身份不要求每轮带全部历史；也不能不核实容量就静默丢掉关键要求或证据。

### 5.5 简洁合同已有，实际产物仍偏长

规则已明确简洁评分报告不要求旧长目录／全量ID，但正文仍约6090字符、全文10485，重复说明和明细增加了生成与检查负担。800—1500字符可以作为试验建议，需明确正文／明细边界与业务完整性，不是立即硬裁剪。

## 6. 运行版本为什么重要

📎 E08把这次任务绑定到bundle0.1.87与r8，并有模块求值哈希；不宜再将本次故障笼统解释为未加载新版本。业务请求使用opencode-go/deepseek-v4.1-flash；开发Pi的模型是另一层。

0.1.87重点修复R30/R31原生续接边界，没有完整处理本次锚点、事实证明关系、问题身份和最终交付说明。85项隔离程序检查不能证明真实Judge不会误读；上一轮静态复评范围也不能扩大成全部业务通过。

## 7. 三条修复主线具体要做什么

### P0：正式保存与最终说明一致

📍 2026-09-24已整理为[P0交付真实性修复指派任务](../01-指派任务/02-交付真实性修复任务.md/01-指派任务.md)，待指派执行，尚未实施。[原01 §17.10](../../../old-version/docs/01-证据质量与计分判定方案.md#p0-solution-draft)保留方案讨论依据。以下保留问题层面的目标摘要。

1. 所有入口统一预检基线、修改范围与锚点；能提前发现的格式错误不拖到评审后。
2. 真正章节编辑保护指定范围；数据替换的跨章节更新复用旧哈希约束下的全文版本提交。
3. 提交成功、明确失败、结果未知有可查询事实；失败保留草稿／旧版，重试先核对已有提交。
4. 交付状态与当前版本入口由程序事实决定；模型说明变化，不能以自由总结替代提交结论。

建议验收：成功时正式哈希、被审哈希和入口哈希相同；失败不宣称成功；未知不猜成功；保存后回执丢失不重复提交。后续是否需要改动哪些程序层，以限定排查结果确定。

### P1：事实、Judge与问题身份可信

1. 在现有评分场景提供类型明确的事实引用，让模型选择事实并解释含义，程序维护输入、指标、值和单位。
2. 复合断言明确哪些部分有依据、哪些待语义核验，不由一个matched为整句背书。
3. 可确定性核查的错误评审意见先与事实对照；保留有证据的异议和未解决状态，不新增常驻第二Judge。
4. 内部issue身份、展示编号、重开与复查引用分开；历史不覆盖为另一问题。

建议验收：T0301—T0320正确范围不能被错误修复；总数不变但text/date变化时，对应结论重新核验；同展示编号不同缺陷不串历史。独立记录误放行、误阻断、漏检和错误修复，分母与参考标签要明确。

### P1：降低协议往返和上下文负担

1. 先减少机械搬运：程序从事实引用取得规格／版本，固定覆盖前置，错误精确到字段。
2. 正文与证据含义未变的纯登记修正做适当机械复核；语义／支持关系变化保留必要Judge复查。
3. 当前目标、有效决定、当前稿、来源差异、相关问题和必要事实进入请求；历史完整留存按需回读。
4. 简洁模式分离主报告与长明细，普通追问保持0业务调用并排查多余主Agent往返。

建议验收：在同模型、同输入下保持正确性和正式保存，再比较完整阶段耗时。不能靠跳检、少报问题、提前结束或更换模型混入归因来达标。

**依赖：事实接口和覆盖关系先明确，才能安全减少登记／评审往返。**本页是方案梳理，不是让AI同时实施所有条目的命令。
