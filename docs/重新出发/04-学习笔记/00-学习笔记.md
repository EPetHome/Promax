# 学习笔记：把理解变成可执行的方法

定位：给自己学习、复盘和提炼用，不是默认加载的执行指令。

以下是在你原有五点理解基础上的建议修订，不是对本地实现状态的结论。可以保留原话、理解变化和反例；不要因为一句话出自某个模型，就把它升级成永久规则。

## 1. 大问题拆小：拆成能检验的行为，不只是拆成模块

原理解：找到最直接的问题和最小验证路径，证明假设后开发。

建议修订：先把现象、期望、影响范围和候选原因分开；设计能够支持、否定或区分主要解释的最小验证。验证不足时可以先排查，不必立刻写补丁。

最小不是改动文件最少，而是问题范围清楚、证据能区分原因。一次修复可能跨多个文件，但不顺便优化无关行为。

例子：最终说明错了，先确认最终回复是否收到同一版本的提交结果；不能直接认定“模型不认真”或“上下文缺失”。

## 2. 基线：开始前就应有，不必等假设成功

原理解：假设被证明后，就有一个基线，再沿链路修补。

建议修订：先保存可定位、可比较的当前状态，即使它是失败状态。它包括输入、代码/运行/相关配置身份、原始期望、实际表现和证据。

基线描述“当前实际怎样”；验收标准规定“应该怎样”。两者不能混写，尤其不能为了让当前实现达标而降低标准。

验证支持假设后，还要区分“原因判断受到支持”“代码改了”“修复经验证有效”“整条业务合格”。下一步按依赖和风险选择，不机械地按模块顺序，也允许新反证推翻旧结论。

## 3. 上下文：不靠猜补事实，但允许有标签的不确定性

原理解：上下文不只是提示词，应给正确、精准、有效、确定的信息，避免模型一路猜下去。

保留的核心：上下文是模型当前能看到的工作信息，不是全部历史的简单堆积。需要在执行中维护并按任务读取相关资料。[S3]

需要校准：“完全确定才进入上下文”会误删关键未知、冲突和反证。更合适的要求是：每项重要信息的来源、类型、有效范围和不确定性清楚。

用户对目标和选择有决定权，不意味着用户对运行原因的猜测自动为真。程序返回可以作为该操作实际返回的记录，但是否保存成功、持久化成功或根因成立，仍要看接口契约与相应证据。模型可以做推断和方案探索，只是不能将它们伪装为已确认事实。

旧决定可能仍有效，新材料也可能不适用。不要只按“最新”判断。原始失败、异议和未知不因摘要想简洁就删除；从当前输入移出的历史保持可回读入口。

建议写成规则：

> 可读取的关键事实先核对；确需推断时标明假设及依据；未知按影响处理，不自动猜成功，也不无差别阻塞全部工作。

## 4. 最小完整链路：不是只演示一次成功

原理解：找到 MVP，把一条线走通，为后续提供借鉴。

建议修订：选择窄场景，从真实输入到用户可用成果走通，并覆盖与本轮风险直接相关的失败或未知情况。局部组件的模拟检查可以帮助定位，但不能冒充完整产品验收。

先稳定评分任务不等于放弃其余业务，也不意味着所有复杂情况都必须现在解决。明确本阶段支持什么、失败时怎样表达、哪些还未验证即可。

已有资料明确区分：执行结束、文件保存、局部评审PASS、整个任务合格。[S1 §3.5] 这一边界应进入交付行为与验收，不只是保留成一句话。

## 5. AI出问题：找实际断点，不默认所有问题都来自上下文

原理解：看重要信息在哪丢失、过期、误解，以及为什么没有执行。

建议修订：这是一条很好的排查入口，但还要检查规则是否明确、工具行为是否正确、权限与状态消费是否符合约定。信息都在，模型也仍可能判断错误；程序也可能把正确输出错误地执行或展示。

顺着同一次运行检查“应看到的信息 → 实际输入 → 可观察动作 → 工具真实返回 → 后续消费 → 对外交付”，找第一个可以确认的偏离点。再调查原因，不把第一个报错字符串自动当根因。

不要求AI叙述不可核验的全部思考。要求它交付事实依据、关键假设、反例、验证办法和结果。

## 6. 一条理解怎样晋升为规则

建议记录格式：

理解：
适用情形：
要求的动作：
怎样检查：
例外和不适用情况：
实践证据：
是否进入长期约定：尚未 / 已合并到某条规则。

“不能顺手扩大范围”适合进入长期协作规则；某次特定ID范围算错，更适合成为具体回归用例。不是所有知识都需要塞进默认上下文。

## 7. 自己掌握全局的最低要求

我知道当前阶段要什么；知道哪些行为有证据、哪些没有；知道当前只改什么；知道修改前后的版本和结果；知道下一步为什么值得做。

不要求我记住每个函数和所有日志，也不要求AI永远不犯错。关键是错误可发现、事实可核对、改动可比较、已验证的能力不会只存在于一段旧聊天里。

资料说明：S1和S3见包外层《README.md》的“依据与边界”。这些方法是待实践的工作建议，不是已经证明适用于所有Agent的定律。
