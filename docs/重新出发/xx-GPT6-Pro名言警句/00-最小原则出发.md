**是，你现在应该改变推进方式：不要再把十个问题一起交给 AI，期待下一轮整体变好。**

但我还想帮你把这个想法再往前推一步：

**不是简单地从“十个一起修”，变成“十个逐个修”；而是先建立一个不会随着每次修改而漂移的基准，然后围绕一条完整链路，一次验证一个明确的问题。**

至于“Agent 开发应该以上下文为地基”，这句话有重要的道理，但也容易被误解成：先做一个很强的上下文系统，其他问题就会自然消失。**我不建议你这样理解，更不建议因此启动一次上下文系统大重构。**

结合 Promax 的情况，我认为你现在最需要的是：

> **先固定任务事实和验收标准，再设计每一步需要的上下文；让每次修改都能证明自己解决了什么、没有破坏什么。**

下面我把这个方向讲清楚。

## 一、你现在最痛苦的，其实是“进展无法可靠积累”

你描述的不是单纯的“Bug 太多”。

更难受的是：昨天似乎解决了一些问题，今天又出现类似问题；AI 说已经修了，你不确定它修的是不是原来的问题；下一轮修改后，连之前哪些结论还成立都不清楚。

**这意味着，你不仅在修系统，还在不断重新确认系统到底是什么样。**

从你的描述看，我更倾向于认为，目前有两个相互影响的混乱：

**一个是 Promax 运行时的混乱。** 主 Agent、成员、Judge、程序之间，哪些信息为准、什么结果意味着什么，有些交接没有真正落实。

**另一个是开发过程的混乱。** 你和开发 AI 在长会话里不断追加要求、修复、例外和评审意见，当前目标、有效决定、代码状态、未完成事项容易混在一起。

所以，**只改 Promax 的运行时上下文，不一定能解决开发 AI 遗漏要求；只改开发提示词，也不能修复产品里的版本和提交问题。** 这两层必须分开看。

而且，你并不是完全没有正确设计。你的报告已经明确写了“程序保存并校验权威状态”，也写了“长期保存与每次模型输入分开”。问题更像是：这些原则还没有在每个关键交接点上，变成可以验证的实际行为。 

**因此，接下来不应该继续补一大套原则，而应该挑一条链路，证明现有原则真的生效。**

## 二、“上下文是地基”到底是什么意思？

### 不是“把所有资料都给模型”

上下文工程关注的，不只是提示词怎么写，而是**每次调用模型时，它实际能看到哪些指令、工具、材料、历史和当前信息**。它需要在执行过程中持续整理，而不是开头写一次长提示词就结束。Anthropic 对上下文工程的定义，核心就是这个意思。([Anthropic][1])

但对 Promax，我建议你把下面三件事严格分开：

**系统事实：现在真正成立的是什么。**
例如用户当前要求、有效数据版本、实际保存结果、被评审版本、尚未解决的问题。这些应由各自明确的来源维护。

**模型上下文：为了这一步工作，模型需要看到哪些事实。**
不是完整复制数据库和全部历史，而是给它足够的、当前有效的工作信息，并提供读取原文的入口。

**模型判断：它基于这些信息，提出什么分析或下一步动作。**
这可以是有价值的判断，也可能有误，不能因为模型说出来，就自动升级为系统事实。

例如：

> 用户说“v2 替代 v1”，这是有效要求。
> 成员说“我已经修改好了”，这是成员的报告。
> 提交接口返回失败，这是执行事实。
> Judge 说 PASS，这是对指定范围和版本的评审结论。

**这四件事的性质不一样，不能混成一段聊天摘要，让下一个模型自己猜哪个最重要。**

### 一个具体例子：更新报告时应该给模型什么？

以你的评分任务为例，我建议更新成员收到的工作信息至少能明确回答：

| 模型需要知道的事情 | 在这个任务中应表达清楚的内容                    |
| --------- | --------------------------------- |
| 这次要做什么    | 用修正版数据更新现有报告，不扩展任务范围              |
| 哪份材料有效    | v2 是当前来源，v1 只用于对照，不能合并统计          |
| 基于哪个成果修改  | 明确的旧报告版本，而不是“你之前写的那份”             |
| 已经确认了什么   | 程序核对的数据差异和新统计结果                   |
| 哪些地方允许改变  | 受数据变化影响的统计、表述和结论                  |
| 怎么才算交付    | 必要检查完成，正式保存成功，入口指向对应版本；否则如实报告部分完成 |

这张表是我建议的工作信息结构，不是要求你新增六套存储。

这里真正重要的是：

**模型不用依赖记忆，去猜“现在以哪个版本为准”；也不需要从几十页历史里重新推导这次允许做什么。**

反过来，把之前所有讨论都塞给它，让它自己找最新要求、自己判断哪些旧决定失效，并不等于上下文完整。

**上下文应该是从可靠事实中整理出来的工作简报，而不是用来代替可靠事实的长聊天。**

## 三、第一块地基，不应该是一个“完美模块”，而是一条“最小完整链路”

你提出“先找一个关键环节搞对”，方向是好的。但要避开另一种陷阱：

> 先把上下文模块做到完美，再把调度模块做到完美，再把 Judge 做到完美，最后才连起来。

这样仍然可能出现：每个模块单独看都合理，一组合就出问题。

**我更建议先选一个很窄的业务场景，把它从输入到真实交付完整贯通。**

你已经有合适的场景，不需要重新发明：**评分报告的首次生成、普通追问、v2 更新。** 它的输入、范围和预期行为已经比较明确。

这个阶段，只启用完成这项任务必需的角色。不是删除其余角色，也不是放弃整个产品，而是暂时不让六类业务一起参与验证。对于边界明确的工作，先使用简单、可组合的路径，再根据实际收益增加复杂度，也是成熟 Agent 工程实践中反复强调的方向。([Anthropic][2])

### 这条链路最先要固定什么？

我建议先固定：

> **任务要求 → 当前材料与成果版本 → 实际执行结果 → 检查结果 → 最终交付说明。**

它的作用是让你随时能够回答：

**现在要交什么？依据哪份材料？实际做到哪一步？结果在哪里？为什么能说完成，或者为什么还不能？**

这不是一个额外的“超级控制系统”，而是现有链路必须讲清楚的事情。

### 第一项实际修复，就选“交付状态不能说假话”

上一轮记录中，工作卡已经是“草稿 · 保存失败”，最终回复却说“报告已更新完成”。这正是一个很适合先固定的边界：现象明确，用户影响直接，也容易构造反例。

这次不要顺便优化统计、Judge、模型和报告模板，只先明确：

**正式提交成功时，完成说明依据什么生成；提交失败时，草稿如何保留、如何告知；提交结果未知时，如何表达待核，而不是猜成功或盲目重试。**

还要保留一条边界：**保存成功只是完整交付的必要条件之一，不代表内容自动合格；Judge PASS 也不能替代保存成功。**

这个环节稳定之后，你至少获得了一件非常重要的东西：

**之后即使业务仍然出错，系统也能可靠地告诉你它没有完成，而不是制造一个“看起来完成”的结果。**

这就是能够继续建设的基础。

## 四、以后遇到“AI 犯糊涂”，先不要急着补提示词

我建议你把“AI 又丢细节了”改写成一个可以调查的问题：

> **这条重要信息，是在哪一步第一次丢失、过期、被误解，或者没有被执行的？**

这比“怎样让 AI 更认真”有效得多。

你已经开始留运行痕迹，这是很重要的一步。下一步不是无限增加日志，而是用现有记录，定位**第一次偏离预期的交接点**。

我建议按下面的方法判断：

| 观察到的情况                  | 优先检查什么                   |
| ----------------------- | ------------------------ |
| 重要要求根本没有进入这次模型请求        | 上下文组装、读取入口和必要信息覆盖        |
| 要求进入了，但新旧版本、有效与失效决定混在一起 | 版本绑定、决定来源和过期信息处理         |
| 信息清楚、当前有效，但模型仍做错        | 指令、示例、工具易用性或模型能力；需要针对性测试 |
| 模型提出了不合法动作，程序照样执行       | 工具校验、权限或执行约束，不能只靠提示词     |
| 程序已经记录失败，界面或最终回复仍说成功    | 状态消费和交付说明的权威来源           |

这是我建议的排查顺序，不是说这五类都是你本次已经证实的根因。

拿“保存失败却说完成”来说，至少有两种可能：

**一种是最终回复的模型没有收到保存失败。** 那就先修结果进入上下文的路径。

**另一种是模型看到了失败，仍然根据之前的 PASS 概括成完成。** 那就说明关键交付状态不能完全依赖自由概括，需要由程序控制其真实性。

这两种修法不同。没看实际输入就不断强化“请如实报告”，很可能修不到关键处。

**你应该问的是“模型在这个决策点到底看到了什么、调用了什么、系统返回了什么”，而不是只看它事后解释自己为什么这么做。**

## 五、一次修改的单位，应该是“一个可以验证的假设”

你现在考虑“不全部一起修”，我支持。但“一次只修一个”也要定义准确。

**不是一次只能改一个文件，而是一次只验证一个主要假设。**

例如：

> 假设：最终回复没有以正式提交结果为依据，因此会在保存失败时误报完成。

为验证和修复这个假设，可能确实需要改几个文件，包括结果传递、状态展示和测试。这仍然是一个完整修改。

但下面这些最好不要夹带进去：

> 顺便压缩上下文，顺便换模型，顺便重写 Judge 提示词，顺便调整报告格式。

因为修改后结果变了，你很难知道是哪个变化导致的。保持修改小、可回退，并及时验证组合结果，是小步集成的核心价值之一。([martinfowler.com][3])

### 每一项修复，至少要形成一个短闭环

你可以把开发任务写成这样：

> **本次问题：** 提交失败后仍宣称完成。
> **已知证据：** 对应运行记录和最终回复。
> **当前假设：** 最终说明没有可靠消费正式提交回执，具体路径待源码核对。
> **本次范围：** 只处理提交结果到最终说明的链路。
> **验收依据：** 成功、失败、结果未知时，实际状态与对用户说明一致。
> **不应改变：** 统计口径、角色职责、普通追问不派工、旧版保留。
> **结束要求：** 明确改了什么、实际验证了什么、还有什么没验证。

注意这里的“当前假设”没有被提前写成已确认根因。**开发 AI 的第一步应该是核对假设，而不是顺着任务书里的猜测直接改。**

### 修好之后，必须留下能拦住复发的检查

否则，“修复过”只存在于聊天记录里，未来的 AI 并不知道怎样维护它。

我建议区分三类证据：

**程序检查**验证保存失败、版本不一致、重复提交等明确规则，不必每次都重新跑完整模型业务。

**模型评测**验证模型是否理解更新范围、是否提出无依据的修改、是否正确消费工具结果。

**端到端验收**验证真实运行环境里，用户最终打开的成果和系统宣称的状态是否一致。

不能用其中一种代替全部。OpenAI 的评测指南也强调：应在各阶段建立针对性检查，持续比较变化，而不是用“看起来能用了”作为验收方法；自动评分还需要人工校准。([OpenAI Platform][4])

尤其是你的 Judge：**产品里的 Judge 是被测试对象的一部分，不是天然正确的验收答案。** 上一轮已经出现正确编号范围被改错的情况，应该把这个案例保留为独立反例，而不是沿用该轮 Judge 的 verified 当正确标签。

另外，模型同一个任务不同次运行可能表现不同。因此，一次通过只能算一次通过；重复运行要报告成功、失败及失败类型，不能“跑到成功就宣布修好”。少量重复可以发现明显波动，但不足以证明长期可靠。([Anthropic][5])

**你需要的是让已解决的问题变成以后必须保持的能力，而不是变成越来越长的历史说明。**

## 六、重新掌握全局，不需要你记住所有细节，也不需要再增加十份文档

我觉得你现在很需要减轻一个负担：

**全局把控不等于你必须知道每个函数里发生了什么。**

对你来说，更有用的全局把控是：清楚当前产品范围、哪些行为已经有证据、哪些仍不可靠、现在只在改什么、这次修改会影响哪里。

你已经有产品定义、唯一任务书和 RESULTS，不要再建立一套平行体系。建议只在现有入口里整理出一个**“当前有效状态”首页**，其余内容通过引用下钻。

这个首页可以很短：

```text
当前阶段：
先稳定评分任务的完整交付链路，不扩展其他业务。

当前基准：
本轮对应的代码版本、实际加载版本、模型配置、测试输入。

已验证行为：
列具体场景和证据入口，不写笼统的“模块已完成”。

已知失败与未验证：
保留问题，但明确哪些不属于当前修改。

本轮唯一目标：
修复提交结果与最终交付说明不一致。

当前进展：
已定位／已修改／已静态检查／已运行验证，分别记录。

下一步：
一个明确动作。
```

这是建议的组织方式，不是你当前状态的自动确认。

这里有两条特别重要：

**第一，问题全集是排队清单，不是本轮授权。**
剩下九个问题不是被忘掉，而是明确地暂不处理。AI 读到它们，也不能顺手一起改。

**第二，最新总结不能覆盖原始事实。**
“已修复”后面要有版本和验证入口；找不到依据就写待验证。新会话读取当前状态后，还要核对代码和实际加载情况，而不是盲信上一轮总结。

在长期编码 Agent 的公开实践中，逐项推进、保存进度、结合版本历史恢复工作状态，确实被用来缓解一次做太多和跨会话失去方向的问题。但这些记录的价值在于帮助恢复真实状态，不是让新会话无条件相信旧会话的自我评价。([Anthropic][6])

你现有的开发分工也可以保留：Pi 实施和受影响自检，Codex 按约定独立静态复评，真实运行验收另列。**不要把“代码评审通过”“已经装配加载”“真实业务通过”合并成一个完成状态。** 这与你原来设定的协作边界一致。

## 七、具体到现在，我建议你怎么开始

**先不要发出“请全面优化 Promax”或者“请重构上下文系统”的任务。**

下一轮可以只做这件事：

> **核对评分任务从正式提交结果到工作卡、成果入口、最终回复的实际链路。明确各处以什么事实为准，复现“提交失败仍说完成”，再用最小修改修复它，并保留对应回归检查。其余问题记录但不顺带修改。**

在这个任务中，你就能实际练习“以上下文为基础”的设计方法：

系统先有明确的任务和执行事实；需要回复的模型收到当前有效结果；程序不允许关键状态被自由解释成相反含义；检查验证用户看到的结果是否真实。

这比先设计一个覆盖整个 Promax 的上下文架构，更容易形成可靠成果。

然后沿着同一条链路继续推进：确认每次决策拿到的材料和版本正确，再处理证据与 Judge 的可靠性，之后减少无效回执、重复上下文和耗时。**期间可以一直记录性能，但不要同时改所有优化手段。**

这里也不需要等到“前一项绝对完美”才继续。你需要的是：已知适用范围、可重复检查、明确剩余风险，以及发现回归时能定位和回退。评测应当从已有手工检查和真实失败样本开始，逐步累积，而不是先等一套庞大的评测平台建成。([Anthropic][5])

---

**最后，我最想给你的指点是：你需要放慢的不是推进速度，而是每次修改扩张的范围。**

别把目标设成“让 AI 这次把所有细节都记住”。更好的目标是：

**即使 AI 忘了一条要求，系统也能发现；即使某个环节失败，结果也不会被说成成功；即使换了一个会话，已经确认的事实和已经通过的检查也不会消失。**

这才是你想要的“地基”。上下文是其中重要的一部分，但真正让 Promax 越修越稳的，是**明确事实、有限修改、独立验收，以及让每一次有效修复都能留下来。**
