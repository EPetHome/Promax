# Promax「重新出发」：开发协作 Markdown 起步包

版本：v0.1｜整理日期：2026-09-23｜性质：建议与模板，尚未安装或启用。

本包根据你提供的目录截图、五点学习总结和《Promax 设计与阶段现状报告》编写。没有读取你截图中各目录的正文，也没有访问或修改你的本地仓库、运行测试、确认当前进程。示例不是已授权任务，待填字段不是已经存在的记录。

## 1. 先做什么

先采用最少部分：短入口、基线、一个当前任务。验证记录沿用已有 RESULTS；其他问题简记在清单中；学习笔记留给自己按需阅读。不要先把所有模板填满，再开始解决问题。

这一套文档首先用于“你与开发 AI 的协作”，不是 Promax 产品运行时的存储规范。暂不把它整套塞进主 Agent、业务成员和 Judge 的上下文。

目录如下：

```text
仓库模板/
├─ AGENTS.md
└─ 重新出发/
   ├─ 00-基线.md
   ├─ 01-当前任务.md
   ├─ 02-验证记录.md
   ├─ 03-问题清单.md
   └─ 90-学习笔记.md
```

## 2. 已有项目：不要产生第二份任务书和第二份 RESULTS

你的背景报告已经约定唯一任务书、唯一 RESULTS，以及实施和独立静态复评的职责边界。[S1 §6.3、附录]

因此，Promax 优先采用“接入现有文件”，而不是“全部复制后并行维护”：

| 本包文件 | 在现有项目中的用法 |
|---|---|
| `AGENTS.md` | 审阅后合并到已有项目入口，保留原有规则，不直接覆盖 |
| `00-基线.md` | 作为短导航和已验证能力索引；已有对应页则合并，不另立产品真相源 |
| `01-当前任务.md` | 将有用栏目并入现役唯一任务书；不同时保留两份活动任务正文 |
| `02-验证记录.md` | 将记录格式并入现有 RESULTS；不新建第二套结果台账 |
| `03-问题清单.md` | 已有问题台账就复用；只保留索引和排队状态，不复制详细证据 |
| `90-学习笔记.md` | 对应原“名言警句”，作为个人学习资料，不默认加载 |

先在基线页“当前入口”中绑定核实过的实际路径。原模板任务与验证页可以不复制；已经复制的，应改为只含跳转说明的索引或移出活动目录。

不要仅凭文件名中的“最新”“最终”选权威来源。以已确认的用途、版本和变更记录为准。发现两份现役任务冲突时，先指出冲突，不默默合并，也不擅自替用户选定范围。

## 3. 新项目：采用模板时的最短步骤

先阅读 `AGENTS.md`，再将模板合并或放置在实际项目中。填写基线页的来源入口、代码/输入/运行配置身份，并区分已核对和未知。

只激活一个当前任务：写清现象、期望行为、当前假设、可以推翻该假设的结果、最小验证、允许范围和必要验收。没有源码证据时，可以只授权排查，不急着授权修改。

验证发生后才写结果。任务结束时，把本次版本与证据引用加入基线；旧记录保留。模型任务有波动时记录全部尝试和条件，不只保留成功那次。

本包不要求自动提交 Git、自动部署、自动重启服务或自动运行真实模型。权限由当前任务和已有约定决定。

## 4. 什么文件什么时候读

| 时机 | 读取范围 |
|---|---|
| 开始新任务或恢复会话 | 适用的项目规则 → 基线页的当前入口 → 唯一当前任务 |
| 核对某条事实、排查、实施或复评 | 按任务索引读取相关源码、原始证据和验证记录；阅读范围应足够支持结论 |
| 选择下一项工作 | 问题清单及其关联证据 |
| 学习方法、复盘规范 | 学习笔记 |

“按需”不是只读摘要就判断整份材料，也不是为了短而漏掉关键限制。历史原文保留；未解决问题、关键未知和反证按相关性进入本轮上下文。

## 5. Codex 入口如何生效

OpenAI 文档说明：Codex 启动时构建指令链，发现全局规则及项目根目录到当前工作目录路径上的适用 `AGENTS.md` 等文件；不是自动递归读取任意笔记目录的所有 Markdown。[S2]

因此，将精简入口放在实际适用的项目层级，并让它指向基线和现役任务。不要认为把一个 `AGENTS.md` 放进无关的笔记子目录就会覆盖全项目。已有全局、覆盖文件或更深层规则时，应核对实际生效范围。

新建或调整入口后，在新会话做一次只读检查：

> 请列出你实际加载或读取的项目规则路径、当前唯一任务入口、本轮允许范围与禁止范围。无法访问的文件请明确列出。此轮不修改文件，不运行测试，不启停服务。

此输出只能帮助确认读取情况，不能证明规则永远被遵守。仍要用实际动作、差异和验收检查约束效果。其他开发工具不要假定与 Codex 同样自动加载；使用其已经确认的机制或明确要求读取入口。

## 7. 一条原则怎样变成有效规范

用下面五项检验一条规则是否可用，不要求每条都写成长表：

**适用情形 → 要做的动作 → 可观察的输出 → 怎样检查 → 例外或边界。**

例如，“不要让 AI 猜”可以改写为：涉及当前来源版本和保存结果时，读取对应记录；无法取得时标未知并说明影响；最终说明给出可核对的状态与入口；允许提出有标签的原因假设，但不能把假设写成已经确认的事实。

不要把每次 Bug 都永久写进 AGENTS。单次故障先进入验证记录和回归用例；只有跨任务反复适用的协作规则，才考虑进入长期约定。确定性约束可以落到程序检查时，不要只靠提示词承担。

## 8. 四种任务模式的用法

### 讨论或排查

> 先只读核对当前基线、任务和相关证据。区分已确认现象、候选原因和未知；给出能区分主要解释的最小验证。不要直接修改代码，不要把我的猜测当根因。

讨论未形成实施授权。授权范围内可直接读取的材料，不必逐文件询问；缺少会影响安全、目标或验收的关键信息时，说明具体缺口。

### 实施

> 按已确认的唯一任务书实施。只处理这一个主要行为目标，可修改必要的关联文件；记录实际差异与授权范围内的检查。发现无关问题只登记。需要扩大行为范围、改验收标准或执行未授权操作时，先说明并请求确认。

### 独立复评

> 按当前角色权限，独立检查任务要求、差异、相关实现和证据。不要把实施者“已修”的总结当参考答案。明确静态可确认项、运行待验证项和真正阻断项；不要把设计偏好冒充缺陷。

如果原约定是仅静态复评，这段话不授权重跑测试、模型或服务。

### 交接

> 更新当前任务的简短交接段和实际验证记录：正在做什么、当前假设的证据状态、实际完成和未完成项、相关版本及入口、下一步一个动作。不要生成另一份相互竞争的现役任务书，不把未知写成已解决。

不必要求 AI 写出冗长的全部思考过程。要求可以检查的判断依据、关键假设、反证、行动与结果即可。

## 9. 一个立即可用的启动任务

以下是建议，不是本包自动批准的操作：

> 本轮只做只读排查。围绕“正式提交结果、工作卡、成果入口与最终完成说明是否一致”，找出相关事实源与消费路径。结合已有运行记录，分别说明已经确认的现象、尚未核实的当前状态，以及能区分主要原因的最小验证方法。先不要改代码、部署、启停服务或运行真实模型。将结论写入已指定的唯一任务书和 RESULTS；未指定可写位置时，先在回复中交付。

这个排查任务完成的标志，是证据与下一步清楚；不是 Promax 已经修复。后续实施必须另有明确范围和授权。
