**可以。最合适的整合方式，不是在【基线】【任务】旁边再增加三套“产品、开发、测试”流程，而是让它们共同服务于同一项任务。**

这里有一个关键区别：

**【基线】【任务】【验证记录】负责保存信息；产品、开发、测试负责从不同角度判断和推进工作。**

它们不是两套东西，而是一套流程的两面。

我已经在上一版模板上完成了整合，做成 **v0.2 工作流与 Markdown 模板包**。先把整个关系讲清楚，文末给你实际文件。

## 一、整合后的主线：从一个已知状态，走到另一个有证据的状态

```text
【产品定义与有效决定】
确定方向、预期行为和边界
          ↓
【基线】
现在是什么状态？哪些有证据？哪些还不知道？
          ↓
【当前任务】
这次只改善什么？允许做什么？怎样判断有效？
          │
          ├─ 产品判断：为什么做、应该怎样、做到哪里
          ├─ 开发判断：当前怎样、原因是什么、怎样修改
          └─ 测试判断：用什么例子检查、实际是否符合预期
          ↓
【实施、检查与验证记录】
记录实际改动、实际运行和结果
          ↓
【任务收尾】
明确通过、不通过、待验证和剩余问题
          ↓
【更新基线】
留下新的已知状态和可继续依赖的能力
          ↓
选择下一项任务
```

**一次开发的成果，不只是代码变化，而是“我们对系统的认识和可依赖能力，发生了什么有证据的变化”。**

例如，最后发现原来的原因假设不成立，虽然没改代码，但排除了一个错误方向，也可以成为有效进展。

反过来，改了很多代码，却说不清改善了什么、验证了什么，就还没有形成可靠的积累。

## 二、文件分工保持不变，但把相互关系固定下来

你之前的目录不需要推倒。建议继续保留这些职责：

| 文件或现有入口             | 唯一职责                   | 什么时候更新          |
| ------------------- | ---------------------- | --------------- |
| **`AGENTS.md`**     | 长期协作规则、读取路线、行动边界       | 通用约定确实发生变化时     |
| **`00-基线.md`**      | 当前入口、版本身份、已确认能力、失败与未知  | 开始核对、重要变化和任务收尾时 |
| **唯一当前任务**          | 本轮目标、产品判断、开发判断、验收设计与进度 | 本轮工作推进时         |
| **唯一 RESULTS／验证记录** | 实际操作、观察、结果和证据          | 每次有效检查发生后       |
| **问题清单**            | 其他问题的影响、依赖、排队与解决情况     | 发现问题、调整顺序或关闭问题时 |
| **学习笔记**            | 理解、反例、经验及方法修订          | 有值得总结的认识时       |

**日常主要维护的是“基线—当前任务—验证记录”这三个位置，不是每次把六份文件都写一遍。**

对已有 Promax，继续复用原来的唯一任务书和 RESULTS；将新栏目合并进去，或者让基线指向它们，不再维护第二套活动正文。这也延续了上一版模板的接入方式。

尤其要分清：

> **产品定义保存“应该怎样”；基线保存“当前实际怎样”；任务保存“这次准备改变什么”；验证记录保存“实际发生了什么”。**

这样，AI 不需要在几份内容相似的文档之间猜测谁说了算。

## 三、一次开发，具体怎样从头走到尾？

### 第一步：读基线，确认起点

这一步不是让 AI 全面阅读整个项目。

只确认本轮需要的几个问题：当前目标依据是什么，正在使用哪个代码或运行版本，相关行为有哪些证据，哪些还是未知。

比如：

> 历史运行出现过保存失败，但当前代码是否仍然存在同样问题，尚未核对。

这就是一个合格的起点。**“当前未知”比直接沿用旧结论更有用。**

本步通常只需要核对基线中的入口与相关证据。发现基线过期就纠正摘要，不需要重写整个项目说明。

### 第二步：在同一份任务里，先写产品判断和验收预期

这里把产品与测试视角提前放进来。

产品判断回答：

> 用户遇到了什么问题？希望怎样表现？本轮只解决哪部分？哪些不做？

验收预期回答：

> 哪些具体情况下，系统应该怎样？怎样观察它有没有做到？

**先定义行为和例子，再讨论实现方案。**

例如，目标不应该一开始就写：

> 增加一个完成状态检查器。

这已经预设了解法。

可以先写：

> 正式提交失败或结果未知时，不向用户宣称成果已经完整交付。

之后再由开发判断，需要修改状态消费、版本绑定、回复生成，还是其他位置。

原有任务基准也应继续保留来源与变更记录，不能因为实现困难而静默改变验收。

### 第三步：开发先核对原因，再决定怎样修改

进入开发视角，但不等于立刻写代码。

先区分：

> 已确认的现象是什么？候选原因是什么？哪个最小观察能够区分这些原因？

有足够证据，就确定改法；没有足够证据，就先进行获准的排查或实验。

**这一阶段允许得出“原假设不成立”，也允许得出“现在还无法区分”。**

具体判断写在当前任务里，原始观察和实验结果进入 RESULTS。不要让开发 AI 为了完成“修复任务”，强行把一个猜测写成根因。

### 第四步：小范围实施，并完成授权范围内的自检

实施围绕同一个行为目标，可以修改多个必要关联文件，但不顺手加入其他优化。

例如修复交付状态一致性时，可以同时调整结果传递和界面消费；但不顺便换模型、压缩所有上下文、重写报告模板。

**当前任务记录改动的目的和进度，RESULTS 记录实际差异、检查和结果。**

阶段与授权已经清楚时，可以连续推进，不需要你逐个文件批准。只有目标、验收、权限或关键依赖发生变化时，才需要重新确认。

### 第五步：对照原要求与例子验收，而不是对照“AI 说已修”

检查依据应当是原始目标、有效规则、实际代码与运行结果。

要分别说明：

> 静态上确认了什么？局部程序检查证明了什么？真实运行验证了什么？哪些仍然没有执行？

你现有资料中的开发边界是：Pi 实施、自检和装配，Codex 按约定独立静态复评。因此，加入测试视角，并不自动授权 Codex 重跑模型、测试或服务。

**同样，评审意见也可以错。** 检查失败时，既要调查实现，也要允许核对测试预期是否准确，不能为了过测试降低标准，也不能盲从错误的评审建议。

### 第六步：收尾，把结果写回基线

这是你以前的流程中最值得加强的一步。

收尾不是一句“已经完成”，而是完成四个信息回写：

**RESULTS 留实际证据；任务写本轮结论；基线更新有边界的状态；问题清单标记解决、待验证或暂缓。**

例如：

> 当前代码已经修改，局部检查通过，但真实运行尚未验证。

那么，基线可以更新“当前代码身份”，但不能同时新增“真实交付链路已通过”的能力结论。

**更新基线，不等于一律升级为成功。失败、未知和被否定的假设，也应当成为新的已知状态。**

## 四、最重要的整合点：一份任务，同时承载三个视角

我建议你把唯一任务书组织成下面这样。小任务每项可以只写一句，复杂任务再展开。

```markdown
# 当前任务

任务身份：
关联基线：
当前阶段：
本轮交付与授权：

## 一、产品判断
用户问题或可观察现象：
期望行为与依据：
本轮唯一主要目标：
本轮不做什么：
尚未确定的关键问题：

## 二、预先设计的验收
正常情况下应该怎样：
目标失败或反例应该怎样：
哪些旧行为不应被破坏：
采用什么检查与参考依据：

## 三、开发判断
当前实现与版本：
已确认事实：
候选原因：
能够支持或否定它的最小验证：
拟采取的改法：
必要修改范围、风险与恢复方式：

## 四、实际实施与验证
实际变更入口：
自检记录：
独立复评记录：
真实运行记录：
各项结论与未验证范围：

## 五、收尾与交接
本轮结束结论：
已确认、未解决和未知：
基线与问题清单更新：
下一步一个动作：
```

这里的顺序有意义：

**预期先写，实际结果后写；两者不能相互覆盖。**

同时，测试不是一个独立文件夹里的“最后一道手续”，而是从任务定义开始就参与。

## 五、用一个具体问题，把整套流程串起来

沿用我们讨论过的“交付状态不一致”作为示例，**不据此假定当前代码仍然存在该缺陷。**

### 基线提供起点

> 历史记录存在相关问题线索。当前代码、实际加载版本、是否仍复现，待核对。

### 当前任务限定目标

> 本轮只处理交付状态与对用户说明的一致性，不顺便解决全部保存错误、Judge 质量和性能问题。

这里特别要注意：**底层保存失败，和保存失败后误报完成，可以是两项不同的问题。** 这轮先修后者，不代表底层保存能力已经恢复。

### 产品与测试共同定义行为

| 情况                     | 应有行为                  |
| ---------------------- | --------------------- |
| 必要检查满足，正式保存成功，入口对应当前版本 | 可以说明范围内完成             |
| 正式保存失败，但草稿可读           | 明确说明保存失败，区分草稿与正式成果    |
| 提交结果未知                 | 说明待核，不能猜成功，也不能直接断定未保存 |
| 保存成功，但必要检查不满足          | 可以说明已保存，不能说完整通过       |

这些例子把“状态真实”从一句原则变成了可以检查的行为，也保留了原资料中“执行结束、文件保存、局部 PASS、整个任务合格”之间的区别。

### 开发检验原因

先检查最终回复的实际输入：

> 是否包含同一成果版本的提交结果？

没有包含，调查传递路径；已经包含，调查结果消费或最终说明约束；没有留存输入，就明确证据缺口。

不要一开始就指定“再加一条提示词”。

### 验证后分别回写

假设最后只完成了代码修改与局部检查，那么：

**任务写：** 已修改，局部检查通过，真实运行待验。

**RESULTS 写：** 对应版本、输入、操作、输出和结论。

**基线写：** 当前存在候选修复；不能沿用为真实业务已通过。

**问题清单写：** 待验证，而不是已解决。

这样，即使换了会话，下一个 AI 也知道究竟走到了哪一步。

## 六、出现问题时，不要每次重新开一条“最终修复任务”

整合流程还需要明确“退回哪里”，否则仍然会不断扩张。

| 遇到的情况      | 应该退回或转到哪里          |
| ---------- | ------------------ |
| 预期行为没说清楚   | 回当前任务的产品判断         |
| 原因假设被否定    | 更新同一任务的开发判断，保留反证   |
| 同一问题验收失败   | 回相关实施环节，追加验证记录     |
| 无法进行必要验证   | 保留待验证或受阻，说明缺口      |
| 发现无关新问题    | 进入问题清单，不顺手实施       |
| 发现测试标准可能错误 | 回原要求核对，必要时记录有效变更   |
| 用户暂停或切换目标  | 保存当前任务状态，再变更唯一活动入口 |

**同一问题的返修，继续在同一个任务中推进；新目标才进入新任务，并保留旧记录。**

另外，“一个任务结束”和“一个问题解决”必须分开。

排查任务可以结束，但问题还没修；实验任务可以结束，但方案还没采用；实施任务可以交接，但业务仍待验。

这能避免为了让任务显示“完成”，不断扩大修改范围或降低检查要求。

## 七、落地时保持轻量：三处常用，其余按需

我建议你平时只盯住三个问题：

**开始时看基线：** 我们站在哪里？

**工作中看任务：** 这一轮只做什么，为什么这样做？

**结束时看记录：** 实际发生了什么，有什么证据？

`AGENTS.md` 不需要每轮改；学习笔记不需要每次加载；问题清单也不是当前全部工作授权。

下一轮模型需要的上下文，就从这三处整理：

> 当前目标与权限、相关版本、已经确认的事实、当前假设与反证、实际进展、未解决问题、下一步动作。

完整历史保留，必要时回读，不需要每次全部注入。这个安排延续了你原有“长期保存与每次模型输入分开”的方向。

**流程的轻重跟着风险走，而不是跟着文件数量走。** 改文案可以很短；涉及版本、取消、保存和外部副作用，就需要更明确的失败与恢复检查。
