### Nexus 方案说明

- **前置权限**：Nexus 默认会话档位会拒绝全部命令（报 `Permission denied by Bash allow rules`），需先在输入框把「当前 Session 权限」切为「完全访问」。这是宿主安全设计，安装器不绕过。
- **同名技能覆盖**：`hosts.json` 的 `replace_existing_skills` 默认开启。已有同名技能（含此前从 Git 导入的旧版）先完整复制到 `~/.product-agent/backups/<时间>/skills-before/`，再经 `import-local` 覆盖（Nexus 按 owner + 技能名更新登记）；宿主拒绝重复导入时原位替换文件。输出 `replaced_existing_skills` 列出被覆盖的外来技能，`previous_skill_backups` 列出备份。原先绑定这些技能的旧 Agent 会随之使用新版内容。关闭该开关则改为发现同名外来技能即停止、不做修改。
- **步骤**：运行时装到 `~/.product-agent/nexus-runtime/2.1.5`（Nexus 会话中 `~` 为宿主运行时主目录）→ `nexusctl skill import-local` 导入 29 个技能 → 创建或按名称复用 7 个 Agent，写入 AGENTS.md（专家定义正文 + Nexus 协作说明）→ 按 catalog 分工绑定技能 → 合并 6 个 Hook 到各 Agent 的 `.nexus/settings.json`（保留宿主写入的 memory/runtime 等键；实测运行时只从 settings.json 加载 command Hook，settings.local.json 里的 hooks 不生效，旧版误写的条目会被清除）→ 创建或补齐群聊。
- **分工**：主理人绑定 product-agent、telemetry-tracker；六名成员按 `runtime/catalog.json` 的 agent 字段绑定其余 27 个业务技能，分工写在 `hosts.json` 的 `team`。
- **回滚口径**：nexusctl 不提供删除 Agent/技能，Nexus 上不做整体回滚。失败时恢复本次改写的 Hook 配置、人设与运行时，已创建的 Agent、已导入的技能保留并列在输出 `retained` 中；修复原因后重跑同一命令，按名称复用补齐。
- **升级**：已由本包导入的技能再次导入；宿主不接受重复导入时，原位替换文件并保留宿主元数据，旧文件备份到 `~/.product-agent/backups`。
- **技能执行授权**：技能在后台 fork 子会话中执行，没有审批界面，未授权命令会被直接拒绝。安装器导入技能时按 `hosts.json` 的 `skill_frontmatter` 在 Nexus 版 SKILL.md 头部写入 `allowed-tools: Bash(python3:*)`，技能执行期间放行 python3 脚本，其余命令仍受宿主权限控制；包内源文件与 WorkBuddy 安装不受影响。内联技能的回执命令在 Nexus 上以 `python3` 开头，落在同一授权内。**不要在 Nexus 中对单条命令点「批准」**：批准会写入技能目录 `.nexus/settings.local.json`，使该目录只放行白名单命令。
- **超大 tool_response**：Nexus 的 Skill 返回值内含 fork 子会话完整消息（可达数 MB），`hook.py` 读取上限提高到 64MB，并在解析后丢弃 `tool_response.messages`，只用最终回答判定完成。子会话记录按技能复用且只增不减，`~/.nexus/users/<owner>/runtime/projects/*-skills-<技能名>/skill-*.jsonl` 会越积越大，导致每次调用返回更大、主会话上下文膨胀；必要时在 Nexus 中开新会话或清理该记录文件（属宿主行为，安装包不动它）。
- **未收到 context 时**：`collection.md` 要求技能不得搜索环境变量或文件寻找 run_id，直接交付并注明“本次统计未登记”，避免子会话反复尝试命令。
- **群聊协作开关**：建群后经 `nexuscfg apply`（rooms.set_collaboration_policy，仅主 Agent 会话可执行）打开「未 @ 时由群主接管」和「允许成员私信协作」，读回确认后输出 `room_policy.status=applied`。未开启时群里不带 @ 的消息只会得到“请使用 @AgentName 指定要对话的成员”。设置失败不影响安装结果，输出 `manual_required` 与手动步骤。
- **生效**：新开会话即加载 Hook，无需重启 Nexus。
- **待实测**（2.1.4 未在真实 Nexus 上执行）：Hook 在 Nexus 会话中的实际触发；fork 技能完成回执格式（hook.py 依据 `completed (forked execution).` 判定）；沙箱对飞书回传的网络放行；`import-local` 对同名技能（本包或外来来源）的覆盖行为；覆盖外来 Git 技能后宿主的更新检查是否会拉回旧版；会话沙箱对其他 Agent 工作区 `.nexus/` 的写入权限。

飞书日期列的显示由多维表格的「文档时区」决定，单改安装包不能改变该设置。统计文档应统一设置为 Asia/Shanghai（UTC+8）；同一文档的所有使用者及历史日期记录共同生效，无需修改个人电脑时区、重传历史记录或给时间戳加小时。

完整自测是可选的开发回归，不是安装前置条件。直接安装使用包内“一键安装提示词.txt”，安装器自身的完整性、权限和读回校验仍会执行。仅在主动选择自测时，分四次独立命令调用，按顺序执行；每段结束后检查对应的 `REQUESTED STAGE PASSED: 阶段名` 和真实退出码0，再运行下一段：

```sh
python3 -u test_distribution.py --stage distribution
```

```sh

```

```sh

```

```sh
python3 -u test_distribution.py --stage hooks
```

每次 WorkBuddy 命令调用明确设置180秒超时（宿主支持时），不要把四段拼在同一条命令里。`-u` 让日志及时输出；不要添加 `-O`、`-OO` 或启用 PYTHONOPTIMIZE，自测入口会拒绝关闭断言的运行方式。省略 `--stage` 会显示用法并非零退出，不自动跑完整套件。普通终端需要完整回归时显式执行 `python3 -u test_distribution.py --stage all`。

任一阶段异常、非零退出、超时或缺少完成标记，都停止后续阶段，只记录实际结果，不重复尝试。局部 PASS、工具调用成功、旧版验证记录均不能代替本次完整结果。不要追加 echo、管道或 `|| true` 覆盖 Python 的失败退出码。只有四段均完整通过才报告离线自测通过；单段超过时限仍属未完成，应保留日志反馈。

需要安装时本人每次都重新提供三项真实身份（包含重装、升级和 `--test`）；不得从旧 profile 推断。安装提示词先用宿主弹窗提醒一次，再在对话里请本人回复三项并等待；不要求先运行上述自测：

```sh
python3 -u install.py --name "本人姓名" --department "本人部门" --person-id "本人稳定工号"
```

Windows 若没有 python3，使用已验证的 `python` 或 `py -3`。安装器会记录实际解释器绝对路径，分发包本身不依赖发布者电脑路径。无需第三方 Python 库。不要单独复制 skills：那样会缺少原生 Hook。

默认目标为当前用户 `~/.workbuddy/skills`，运行时在 `~/.workbuddy/product-agent-runtime/2.1.5`，Hook 写入 `~/.workbuddy/settings.json`。自定义目标可传 `--destination` 指向实际 WorkBuddy skills 目录，配置仍位于该目录父级。只有确实为 WorkBuddy 使用的目录才有效。

安装器先将原配置按字节原样写回，检查与实际安装相同的配置写入权限；尚无配置时预检建立空 JSON 配置，安装失败时尝试恢复原先缺省状态。宿主要求授权时使用正常授权流程；授权被拒时尚未更换技能和运行时。不要关闭沙箱或安全保护。

同一个安装包用于 macOS 与 Windows，不按操作系统分包；安装器自动识别。Windows 安装修正：技能、运行时、专家团的备份、替换和回滚，统一对原生 WinError 5／32／33 做有限重试。首次立即执行，失败后最多等待 50／100／200／400／800 毫秒重试，总等待不超过 1.55 秒／次目录移动。持续拒绝仍抛出原始异常并尝试回滚；其他错误、非 Windows 环境、没有原生错误码的宿主拒绝立即停止。重试不重新发起安装，不新增安装事件。配置写入授权仍走正常流程，不停止系统服务、不更改安全设置。

更新前的技能、配置和被替换的运行时保存在 `~/.workbuddy/skill-backups`；失败时通过移动文件恢复，不递归删除新文件或旧备份。安装过程只清理空临时目录；保留的临时文件通过 `cleanup_pending` 输出。文件和配置校验通过后，仅清理受阻不会把安装结果改成失败；真实安装失败仍记录失败，原始错误与 `recovery_errors` 分开保留。备份不会自动批量清除。

## 整包安装统计

`install.py` 是统一安装入口，文件、运行时与 Hook 配置安装并读回校验成功后，自动记录一条成功的整包安装事件。29个技能合计为一次安装。不要手动复制技能目录绕过安装器；下载、解压、离线自测、查询状态不计安装。

第四张表“人员登记”优先按工号匹配，其次按同名且没有工号的唯一行覆盖；同名但工号不同新开行。仅正式成功安装时登记，覆盖旧编号时精确改写 table3/table1 的历史编号，最后改 table4；候选重复则新开或保留 G 行并记待人工核对。重装与升级不新增同一工号人员。姓名、部门、首次/最近成功安装时间及最近成功版本由第三张表公式汇总，不依赖技能调用明细。没有部门全量名单时由领导人工核对。

第三张表“安装记录”提供“安装总览”“安装明细”“测试记录”视图。总览自动汇总正式成功安装次数、安装人数、实例数、首装/重装/升级次数，并单列失败安装次数。明细可按版本、安装人、部门和安装类型筛选。

每次实际运行安装器生成独立事件 ID：以上次成功安装版本判断首装、重装或升级。尚无成功记录时，首次接管已有安装所读到的版本作为基线保留；失败遗留的新版本文件不改变该基线。同版本成功再安装属于重装，会计一次新的成功安装；断网或响应丢失后补传沿用原 ID，不重复计数。同一用户同一安装目录的实例 ID 在升级/重装后保留；换电脑或清除本地状态会生成新实例，不等同硬件设备数。历史失败记录保持原结果，不改写为成功。

采集姓名、部门、稳定人员编号、安装版本/时间/结果、原版本与安装类型、安装目标宿主/版本、操作系统/Python版本、随机安装实例 ID；不采集硬件序列号。安装人来自本人填写，未接入飞书登录认证。安装失败尽量留存失败事件；身份/配置校验未通过、脚本未能启动不形成安装事件。进程被强制杀死或断电，事件可能停留“安装中”，不会算成功。

安装器先落盘事件，再后台发送。网络失败不撤销已完成的安装。`hook.py status` 的 `installations` 查看本机记录和清理／恢复信息；`hook.py sync` 使用原事件补传。须核对真实退出码0、本次事件 `result=成功` 和 `delivery=verified`；失败事件也可以回传核验，不能只凭 verified 判断成功。联调安装显式加 `--test`，与正式汇总隔离；普通安装不要添加该参数。

## 运行机制

1. 模型选择并调用宿主 Skill 工具。
2. PreToolUse 原生 command Hook 根据宿主 session_id 和 tool_use_id 建立唯一调用，落本地事件，并向业务技能注入运行编号和输出目录。缺少本人身份或必要事件字段时明确阻止该次调用。
3. 三项生成 Skill 内联执行，加载不表示完成，使用 context.receipt_cli 的 checkpoint / complete；其余 24 项业务 Skill 仍 fork。父层传完整任务与材料路径，不重复派发生成子模型。
4. fork 由 PostToolUse / PostToolUseFailure 记录结果；内联以显式 complete 结束，同一条运行记录累计阶段产物和检查。Hook 检查对应编号、状态和实际产物。回执缺失、编号不符或产物核验异常时，执行状态记为“待核验”，结果校验记为“异常”，校验说明保留具体原因；结束时间、耗时和产物数量留空，表示尚未确认，不表示没有产物。真实的业务失败或宿主工具失败仍为“失败”。这是一条 Skill 调用的状态，不是整个任务或专家成员状态；不要为修复统计重复运行业务，也不要自行改判成功。
5. 后台 Python 使用既有应用凭据获取 tenant_access_token，创建或更新原明细行，并逐字段读回。访问令牌只存进程内存，不随安装包分发。
6. 总统计表沿用飞书公式从明细自动汇总；不会在多个使用者电脑上各自执行“总数+1”。

回传脚本由宿主执行，模型不再负责调用 start/finish。业务状态仍来自业务执行结果，文件存在检查不等于内容质量验收，也没有新增独立 Judge 智能体。

只覆盖本包通过宿主 Skill 工具调用的能力。直接读 SKILL.md、普通聊天、未实际触发 Skill 的回答不会采集。父子关系通过父调用的本地有效上下文关联；未传父上下文时不猜测关系。结果回执不合规时记为待核验，并单列校验说明；不会据此推断业务失败。

## 宿主来源

新版使用明细新增“宿主来源、宿主版本、采集方式、来源判定”。本版安装器明确绑定 WorkBuddy，原生事件记录 WorkBuddy；采集方式区分原生Hook与原生Hook-内联任务，来源判定为安装目标绑定。macOS 读取应用包版本；读不到的版本写“未知”。这不是对任意 Agent 的自动识别，其他宿主尚未接入。

旧“来源”列保留用于已发出版本兼容，在默认视图隐藏。已有历史记录依据旧标签迁移，判定明确写“历史标签推断”，无法确定的采集方式或版本为“未知”。旧版本后续写入的记录可能没有新字段，需要升级客户端或由管理员再次迁移；不会伪造成新版识别结果。管理员脚本调用默认来源未知，不再默认冒充 WorkBuddy。

## 查询与恢复

使用安装器输出的实际解释器和运行时路径：

```sh
python3 ~/.workbuddy/product-agent-runtime/2.1.5/hook.py status
python3 ~/.workbuddy/product-agent-runtime/2.1.5/hook.py sync
```

上述 `~` 表示当前用户；Windows 使用安装器输出的实际路径。status 为本地只读；sync 补传原回执。后台失败不会长时间阻塞业务，SessionStart、Stop、SessionEnd 会唤起恢复。离线事件保存在本人 `~/.config/product-agent-feishu-full/hooks`，传输回执在同级 receipts。安装事件在同级 install-events，传输回执在 install-receipts。

只有 delivery=verified 才表示本次结果已读回核验。强制终止进程、断电或宿主未发结束事件时，记录可保持运行中，不能自动宣布成功。查看 hook-error.json / last-error.json 及 WorkBuddy 原始错误定位；不要无限自测或关闭安全保护。
