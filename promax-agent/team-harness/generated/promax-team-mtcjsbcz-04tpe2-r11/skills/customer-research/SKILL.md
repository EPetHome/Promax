# 客户研究报告

## 何时使用

当任务要求基于已经提供的客户研究材料完成以下任一工作时使用：

- 整理访谈、问卷、客服记录或会议摘录；
- 识别客户角色、场景、动机、痛点和候选需求；
- 构建可回到原文的证据矩阵；
- 明确样本限制、冲突、缺口和待验证项；
- 向需求管理、产品探索或产品方案角色移交研究结论。

以下任务不使用本 Skill：竞品对标、网页补采、PRD 或原型生成、需求最终排序、正式需求验收。任务同时包含这些目标时，只完成客户研究部分并把其余目标移交协调者。

## 输入契约

1. 唯一事实来源是协调者任务包中逐项列出的用户原始输入文件或原始附件。
2. 不读取或采信 source-ledger、其他 Agent 对话、推理过程、中间草稿、既有验收报告或生成 Agent 自评。
3. 每份输入先登记为 `SRC-001`、`SRC-002`……；每条可引用摘录登记为 `E-001`、`E-002`……。
4. 输入不是逐字稿、缺少样本总数、角色或时间范围时，必须在报告中标为“未提供”，不得补造。
5. 外部网页、搜索结果、指标或客服数据只有在任务开始前已作为原始输入明确提供时才可使用；否则写“未验证”，不得自行联网补采。

## 唯一输出

只写协调者指定的 `deliverables/{task_key}/customer_research.md`。不得生成 PRD、竞品报告、需求管理记录或其他成员文件。

报告标题可带主题，但以下二级标题必须逐字保留且顺序固定：

```markdown
# 客户研究报告：{主题}

## 0 交付状态
## 1 输入证据清单
## 2 样本与场景
## 3 样本边界与外推限制
## 4 访谈摘要
## 5 关键发现
## 6 痛点与候选需求
## 7 证据追溯矩阵
## 8 矛盾、缺口与未验证项
## 9 下游移交
## 10 逐项自检
```

输入没有支撑某节时保留标题并写“未提供”或“不适用”，不能删节。

## 共享证据规则

- `## 1 输入证据清单` 必须列出每个 `SRC-*` 的文件路径、材料类型、时间范围、样本标识和限制。
- `## 5 关键发现` 使用 `F-001` 起的编号；`## 6 痛点与候选需求` 分别使用 `P-001`、`N-001` 起的编号。每个编号所在行必须直接列出支撑它的 `E-*`，不能只在段尾笼统挂证据。
- 任何发现、痛点、候选需求、比例或优先建议都必须引用一个或多个 `E-*`。
- `## 7 证据追溯矩阵` 至少包含：结论编号（`F-*` / `P-*` / `N-*`）、结论类型、`E-*`、`SRC-*`、输入原文与位置、事实/推断/建议、适用样本、置信限制。
- 同一摘录可以支撑多条结论，但每条结论必须独立说明推导，不得只写“见上文”。
- 脚本输出只是候选抽取，不是新的事实来源；最终结论仍须回到原始输入。

## 样本边界真值表

先定义：

- `sample_size`：输入中可唯一识别的样本数；拿不到时写“未提供”。
- `observed_count`：明确支持某结论的唯一样本数。
- `support_rate = observed_count / sample_size`：仅当两者都可计算时填写。

对每条跨样本结论逐行执行：

| 条件 | 结果 |
|---|---|
| `sample_size` 未提供 | 不计算比例，不声称覆盖总体 |
| `observed_count > sample_size` | fail，修正计数后才能交付 |
| `observed_count = 1` | 标“个案”，不得写成普遍偏好 |
| `1 < observed_count < sample_size` | 只描述“本批样本中 x/n”，不得外推总体 |
| `observed_count = sample_size` | 只描述“本批已提供样本全部如此”，仍不得外推总体 |
| 存在相反证据 | 同列正反证据并标冲突，不得取多数直接覆盖少数 |

`## 3 样本边界与外推限制` 必须给出本任务的实际代入表；表头逐字包含 `结论编号`、`observed_count`、`sample_size`、`计算式`、`允许表述`、`禁止表述`。可计算时两个计数单元格只写非负整数；无法计算时两个计数都写“未提供”，不得用估算值代替。

## 工作流

### 1. 输入盘点

逐份读取任务包点名的输入，建立 `SRC-*` 清单和样本去重表。先记录缺失、矛盾和材料粒度，再开始分析。

### 2. 证据编号

把可定位的原文摘录编号为 `E-*`。引用必须包含输入文件、章节/行或样本标识；不能只写一个不可复查的总结句。

### 3. 语义分析

按需读取以下资源：

- 访谈与记录方法：`resources/references/interview_framework.md`
- 痛点分类：`resources/references/pain_point_taxonomy.md`
- 需求与解决方案区分：`resources/references/demand_extraction_rules.md`
- BEIK 客户画像：`resources/references/customer_shell.md`
- 行为 Persona：`resources/references/user_persona.md`
- KANO 建议：`resources/references/demand_layering.md`
- 多源互证：`resources/references/triangulation_guide.md`

方法标签不能代替证据。画像、KANO、严重度或置信度只有在输入足以支持时使用；否则标“待验证假设”。

### 4. 形成结论

先写样本边界，再写发现、痛点和候选需求。事实、分析推断、产品建议和未验证项必须分栏或显式标注。不得把候选需求写成已经批准的需求，不得替协调者裁定最终优先级。

### 5. 多源互证

仅当任务包含访谈之外的原始证据或指标时，使用 `resources/scripts/triangulate_insights.py` 做候选矩阵，再回到原始输入逐项复核。没有这些材料时明确写“未执行多源互证”，不得输出 S/A 级高置信结论。

### 6. 写入与回读

写入唯一输出路径后回读全文，逐项执行下方自检。失败项必须修正；当前无法修正的写入“未验证项”，不能伪装成通过。

## 逐项自检

`## 10 逐项自检` 必须包含下表并填写 pass/fail；不得只写“已自检”。

| 自检项 | 通过条件 |
|---|---|
| CR-01 固定章节 | 0–10 节标题逐字存在且顺序正确 |
| CR-02 输入闭集 | 报告只使用任务包点名的原始输入 |
| CR-03 证据可定位 | 每条关键发现、痛点和候选需求均有 `E-*`，矩阵可回到 `SRC-*` 原文 |
| CR-04 样本计数 | 每条代入均满足 `0 <= observed_count <= sample_size`，未知时不计算 |
| CR-05 外推边界 | 个案与本批样本结论没有改写为总体结论 |
| CR-06 冲突诚实 | 正反证据并列，未替用户拍板 |
| CR-07 分类诚实 | 事实、推断、建议、未验证项没有混写 |
| CR-08 角色边界 | 未输出竞品结论、PRD 或最终优先级裁定 |
| CR-09 文件责任 | 只写指定 `customer_research.md`，回读后确认非空 |

只要任一项 fail，交付状态就是“未通过自检”；不得自行宣布 Judge 通过。

## 失败与回退

- 输入缺失：保留固定章节，列出缺口和受影响结论，不补造。
- 计数冲突：停止比例与总体表述，回到样本标识逐条去重。
- 证据冲突：并列证据、标明影响，不按多数替用户裁决。
- 脚本失败或格式不适配：停止使用脚本，手工完成证据编号与矩阵；不得把脚本错误隐藏成分析结果。
- Judge fail：仅按协调者转交的可定位缺陷修复原文件；最多修复两轮，申诉必须带输入反证。

## 可选脚本

脚本仅用于机械初筛，使用前先确认输入格式，使用后必须语义复核：

```bash
python3 resources/scripts/analyze_interview.py --input interview.txt --output report.json --json
python3 resources/scripts/extract_pain_points.py --input interview.txt --output pain_points.md
python3 resources/scripts/build_customer_shell.py --input customer_profile.txt --output shell.md
python3 resources/scripts/triangulate_insights.py --interviews report.json --evidence evidence.json --metrics metrics.csv --output triangulation.md
```
