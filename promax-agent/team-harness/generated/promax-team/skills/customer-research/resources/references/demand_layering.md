# 需求分层（KANO 模型 + 优先级）

> **为什么分层**：用户表达的"想要" ≠ 真实价值。同一条需求，在不同产品阶段、不同用户预期下价值完全不同。
> **产出**：为每条候选需求标注 KANO 类别（M/P/A/I/R），并给出优先级建议，供主智能体做最终裁定。
> **对齐市面标杆**：参考 VoC 平台（Chattermill/Thematic 等）的做法——先自动分层初筛，再由人工语义复核，结论必须可回溯到原文证据。

---

## 1. 五类需求定义

| 类别 | 代号 | 含义 | 满足时 | 缺失时 | 典型例子（网盘） |
|------|------|------|--------|--------|-----------------|
| 基本需求 | **M** Must-be | 用户认为"必须有"的属性 | 无感（理所当然） | 强烈不满 | 上传/下载 |
| 期望需求 | **P** Performance | 用户明确提出、越多越好 | 越满足越满意 | 不满意 | 容量、速度 |
| 兴奋需求 | **A** Attractive | 超出预期、用户没意识到 | 惊喜（WOW） | 无所谓 | 智能分类、极速下载 |
| 无差异需求 | **I** Indifferent | 有没有都行 | 无感 | 无感 | 界面主题色 |
| 反向需求 | **R** Reverse | 做了反而反感 | 反感 | 无感 | 频繁弹窗引导 |

**核心判定直觉**：
- 用户**骂的是 M**（缺失会炸）；
- 用户**比的是 P**（"别家更快/更准"，满意度线性）；
- 用户**惊叹的是 A**（"没想到还有这个"）；
- 用户**无视的是 I**（做了白做）；
- 用户**烦的是 R**（做了反而掉分）。

## 2. 访谈语言信号速查（从原话初判类别）

| 用户原话信号 | 初判 | 解读 |
|-------------|------|------|
| "必须要有""没有根本没法用""这是底线" | **M** | 基本需求缺失，当前正承受不满 |
| "起码得……""连……都没有" | **M** | 把缺项当理所当然，被剥夺感强 |
| "别家都能……""希望更快/更准/更大" | **P** | 对比型期望，满意度线性，最常被直接表达 |
| "越多越好""能不能再……" | **P** | 增量型期望 |
| "没想到还能这样""居然可以""太惊喜了" | **A** | 兴奋点，差异化机会（但用户未主动要求过） |
| "如果能……就好了，不过现在也还行" | **A**（弱） | 隐含惊喜，表达力弱，需交叉验证 |
| "有没有都行""无所谓""不太关注" | **I** | 低价值，避免过度投入 |
| "最烦……""不要……""弹窗太多了" | **R** | 反向需求，做了适得其反 |

> ⚠️ **初判只是信号**：机械信号必须经 LLM 语义复核，结合上下文（抱怨强度、行为证据、表达力级别）修正，并回挂原文证据。

## 3. 需求迁移规律（时间维度）

```
兴奋需求 A ──(竞品跟进/用户习惯养成)──▶ 期望需求 P ──(行业标配化)──▶ 基本需求 M
```

- 今天让人"WOW"的功能，3 年后是"必须"；今天的 M，是明天的入场券；
- 落地判断：**判断类别时标注"当前时点"**，避免按 3 年前的心智分类；
- AI 类需求尤其明显：语音交互在车载导航已是 M，在社交 App 可能是 I。

---

## 4. 优先级规则

**基础排序**：`M > P > A > I > R`

| 优先级 | 类别组合 | 说明 |
|--------|---------|------|
| 🔴 P0 | M 缺失 + 高严重度/高频次 | 不做会持续失分，优先补齐 |
| 🟠 P1 | P 中的高性价比项 | 满意度线性，做了有回报 |
| 🟡 P2 | A（低成本高惊喜）| 差异化亮点，控制成本 |
| ⚪ P3 | I / 低价值 P | 暂缓或拒绝 |
| ⛔ 拒绝 | R | 明确不做，除非有强战略理由 |

**修正因子**（供主智能体最终裁定，客研仅提供建议）：
- 成本：A 类若研发成本过高，降级处理；
- 战略：M 缺失但有替代方案时，可暂缓；
- 时机：结合贝壳图外部环境（E），判断变革窗口。

## 5. 定量补充：better-worse 系数（问卷法）

当需要量化优先级或向领导汇报时，用 KANO 问卷 + 系数：

**问卷每题三问**：
1. 正向："如果提供【功能 X】，你的感受是？"（非常喜欢 / 理所当然 / 无所谓 / 勉强接受 / 很不喜欢）
2. 反向："如果不提供【功能 X】，你的感受是？"
3. 重要度："【功能 X】对你来说多重要？"（1-9 分）

**分类参照表**（正×反 5×5 → 类别）：经典 KANO 评价表，正向与反向组合落在 M/P/A/I/R/Q(可疑)。

**系数计算**（N = M+P+A+I 计数之和）：
```
Better（满意系数）= (A + P) / N        ← 提供时满意度提升幅度
Worse（不满意系数）= -(M + P) / N      ← 缺失时满意度下降幅度（绝对值越大越关键）
```

**四象限判读**（横轴 Better、纵轴 Worse 绝对值，均值为参考警戒线）：
- 右上（Better↑ Worse↑）：P 类，优先投入；
- 右下（Better↑ Worse↓）：A 类，低成本差异化；
- 左上（Better↓ Worse↑）：M 类，先补齐；
- 左下（Better↓ Worse↓）：I 类，砍掉。

## 6. 从访谈记录判断类别的操作流程

```
① 机械初筛：脚本提取候选需求 + 信号词（§2 速查表）
② 语义复核：对照上下文判断真实类别（抱怨强度 / 行为证据 / 表达力）
③ 证据回挂：每条结论标注 KANO 类别 + 原文证据
④ 交叉验证：跨受访者/跨访谈出现次数 → 共识 / 个案
⑤ 输出建议：类别 + 基础优先级 + 修正因子说明
```

## 7. 与痛点/需求提取的衔接

| 提取结果 | 常见对应 | 处理 |
|---------|---------|------|
| 痛点（负面信号强） | 多为 **M 缺失** 或 **P 未达标** | 痛点 → 基本/期望需求，P0 候选 |
| 候选需求（直接表达） | 多为 **P** | 满意度线性，标注对比对象 |
| 隐含惊喜（"没想到"） | **A** | 差异化机会，单独标注 |
| 客套认可（"那当然好"） | 多为 I 或 A（弱） | 置信度降级，避免高估 |

---

## 8. 常见陷阱

- ❌ **把"用户说了"当"用户要了"**：表达力 ≠ 价值，客套与真实需求要区分（见 demand_extraction_rules.md）；
- ❌ **把 A 当 P 做**：兴奋需求是"不做不减分、做了大加分"，别用 M 的标准重金投入；
- ❌ **忽视 R**：反向需求往往来自过度设计，识别后应明确"不做"；
- ❌ **不标注时点**：需求类别随时间迁移，报告须注明判断时点；
- ❌ **客研越权裁定**：客研只给类别与建议，最终优先级由主智能体/决策层结合成本战略裁定（边界原则）。
