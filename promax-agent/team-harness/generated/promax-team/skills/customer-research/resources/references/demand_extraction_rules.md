# 需求提取规则（升级版）

> 从访谈语料中把"客户的话"转译为"可进入需求池的候选需求条目"。
> 核心难点：**客户说出口的往往是解决方案，而不是需求**。

## 1. 第一性判别：需求 vs 解决方案

客户说"我要一个一键导出 Excel 的按钮" —— 这是**方案**；背后的需求可能是"我需要每周给老板汇报数据"。

### "为什么-为了什么"五问法（还原真实需求）
对任何一句诉求连续追问（在语料中找上下文，找不到则生成待澄清问题）：

1. 你要这个是为了解决什么问题？
2. 现在没有它，你是怎么做的？（现状成本）
3. 解决了之后，你的工作/生活会发生什么变化？（收益）
4. 这个问题多久发生一次？影响多大？（频次/严重度）
5. 如果只能解决一半，你优先要哪一半？（真实偏好）

### 转译示例
| 客户原话 | 表面方案 | 还原后的真实需求 |
|---------|---------|----------------|
| "给我加个导出按钮" | 增加导出按钮 | 需要周期性生成运营报表供内部汇报 |
| "你们能不能支持批量导入" | 支持批量导入 | 当前逐条录入耗时，需降低录入成本 |
| "希望价格再低一点" | 降价 | 预算有限，需更匹配使用量的计费方式 |

## 2. 需求表达力分级（证据强度）

| 级别 | 信号 | 置信度参考 |
|------|------|-----------|
| L1 明确表达 | 直接提出 + 有具体场景 + 描述使用方式 | 高（0.8-1.0） |
| L2 隐含表达 | 描述了痛点/工作流，未直接提需求但可推导 | 中（0.5-0.8） |
| L3 潜在表达 | "如果能…就好了"、假设性、他人口述 | 低（0.2-0.5） |

> 表达力级别是**起点**，最终置信度还需结合第 4 节多因素综合。

## 3. 痛点 → 需求映射

需求的来源应是痛点，映射关系必须显式记录：

```
痛点（原文+编号）──解决──▶ 候选需求（一句话）
```

示例：
- 痛点 P1（每晚手工统计 2-3 小时）→ 需求 R1：提供自动汇总各店销量并生成订货建议清单的功能。

若一条需求**找不到对应的痛点**，标记为"疑似伪需求"，进入待澄清问题（问清楚动机再决定是否保留）。

## 4. 置信度评分（四因素）

| 因素 | 权重 | 评分说明（0-1） |
|------|------|----------------|
| 表达力级别 | 40% | L1=1.0 / L2=0.65 / L3=0.3 |
| 共识度 | 30% | 提及人数/受访总人数（≥50%→1.0，25-50%→0.6，个案→0.3） |
| 行为证据 | 20% | 有替代方案使用/付费意愿/实际损失描述→1.0；仅口头→0.4 |
| 时效信号 | 10% | 有明确时间要求（"下季度要上线"）→1.0；无→0.5 |

最终置信度 = Σ(因素 × 权重)，分级：
- ≥ 0.75 → 高置信度，建议优先进入需求池
- 0.5-0.75 → 中置信度，进入待澄清
- < 0.5 → 低置信度，仅记录观察

## 5. 需求卡片字段（每条需求统一输出）

```
需求编号：R01
需求描述：（一句话，说清"谁在什么场景要完成什么"）
需求类别：（功能/体验/性能/成本/服务/集成/合规）
来源痛点：P01（关联痛点编号）
表达力级别：L1/L2/L3
置信度：0.82（高）
行为证据：（若有，引原文）
原文证据：（受访者原话 + 来源记录编号 + 段号/时间戳）
状态：候选 / 待澄清 / 已否决
```

## 6. 伪需求检查清单（输出前逐条过）

- [ ] 需求背后有明确任务场景吗？（无 → 待澄清）
- [ ] 是解决方案还是真实需求？（是方案 → 还原后重写）
- [ ] 有原文证据吗？（无 → 标注推断，不得写实）
- [ ] 是否只来自单一受访者且无行为证据？（是 → 标注个案）
- [ ] 是否与已有需求条目重复？（是 → 合并并保留全部证据）

## 7. 需求分类关键词速查（辅助 LLM，非机械规则）

| 类别 | 关键词 |
|------|--------|
| 功能 | 功能、模块、能力、支持、实现、自动化 |
| 体验 | 界面、操作、流程、交互、提示、引导 |
| 性能 | 速度、响应、并发、稳定、容量、加载 |
| 成本 | 价格、费用、预算、计费、性价比 |
| 服务 | 客服、售后、培训、文档、支持 |
| 集成 | 对接、接口、API、数据同步、兼容 |
| 合规 | 权限、审计、安全、合规、风控 |

> 关键词仅辅助定位；**最终归类由语义判断**（如"服务"一词可能指产品功能，也可能指售后服务）。
