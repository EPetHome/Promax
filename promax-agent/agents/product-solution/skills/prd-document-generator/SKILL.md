# PRD 文档生成

遵守 preset persona 的共享证据口径和团队文件责任；本 Skill 不得降低任何反编造、硬信息保留或矛盾阻断要求。负责人指定的 `source-ledger.md` 是唯一共享证据源，PRD 专员只写 `prd.md`，不得修改账本或其他专员文件。

## 交付目标

- 将完整 PRD 写入负责人指定的 `deliverables/<task-key>/prd.md`。
- 文件名固定为 `prd.md`，对接产物类型固定为 `kind=prd`；不得追加时间戳、另存副本或自行上传。
- 只交付 Markdown，不承诺 PDF、DOCX、下载链接或在线预览。
- 对有依据的部分给出可执行文档；对缺口与矛盾明确标记，不用默认值伪造完整性。

## 执行流程

1. 读取负责人指定的 `source-ledger.md`，确认任务类型、目标路径、来源清单、`IN/CON/GAP` 编号和 PRD 文件责任。
2. 对照账本提取全部硬信息：名称、角色、字段、表名、数字、日期、频率、状态、枚举、范围、限制和明确优先级；编号沿用账本，不另建第二套输入事实编号。
3. 必要时只读核对账本列明的原始材料。发现账本与原文不一致时停止受影响结论并报告负责人，不得私自改账本或选边。
4. 只从账本事实生成正文。需要推导、设计选择或测试示例时，使用 persona 规定的类别；新发现的缺口先报告负责人，未回写账本前不得伪装成共享结论。
5. 写入负责人指定目录的 `prd.md`；不要只在对话中展示正文，也不要写流程图、原型或账本。
6. 回读文件，执行本 Skill 的验证清单；发现失败先修改 `prd.md`，再完整复查。
7. 向负责人报告 `kind=prd`、真实文件路径、检查结果、被阻断项和未验证项。

## PRD 必备结构

根据输入内容使用以下章节；没有依据的可选内容写“未提供”，不要凑模板文字。

```markdown
# PRD：{输入提供的名称；未提供则写“未提供”}

## 0. 生成状态
- 状态：完整 / 部分完成（存在 GAP/CON）/ 失败
- 输入事实数：
- 输入矛盾数：
- 被阻断范围：

## 1. 文档信息
## 2. 输入事实与证据清单
## 3. 需求背景与现状
## 4. 目标、范围与非目标
## 5. 用户与业务角色
## 6. 功能需求
## 7. 业务流程与状态规则
## 8. 输入硬信息保留表
## 9. 验收口径
## 10. 输入矛盾、缺口与待确认设计选择
## 11. 追溯矩阵
```

## 内容规则

### 背景、问题和目标

- 只写输入明确陈述的背景、现状问题和目标，并引用 `IN-xxx`。
- 不把“通常存在”“可能需要”改写成该项目已经存在的问题。
- 合理建议放入 `[设计选择 DSN-xxx]`，不得混进已确认目标。

### 功能需求

每项功能至少包含：

| 字段 | 要求 |
|---|---|
| 功能编号 | `F-xxx` |
| 名称与描述 | 引用输入事实或明确推导编号 |
| 优先级 | 仅保留输入值或按输入规则计算；否则写“未提供” |
| 业务规则 | 每条引用 `IN/DER`；冲突项写 `BLOCKED(CON-xxx)` |
| 输入与输出 | 只列已提供内容；缺失写 `GAP-xxx` |
| 验收口径 | 由输入约束转成可观察结果；不能凭空添加指标 |

### 数据库及技术硬信息

- 把输入给出的每个表名、字段名、类型、枚举或接口名逐字保留到“输入硬信息保留表”。
- 为每项注明来源编号及正文去向；不适合进入业务正文的，明确写“仅作为输入事实保留，不在本 PRD 设计技术实现”。
- 不新增表、字段、类型、关系、SQL、索引、接口、技术栈或架构结论。

### 矛盾与缺口

- 对每个 `CON-xxx` 列出冲突双方、证据编号、影响的功能/流程/原型交互和解除条件。
- 不写“暂按某一方处理”。只有输入明确给出优先规则，才能记录解决结果和依据。
- 缺口只描述缺了什么、影响什么；不使用看似确定的默认业务值。

### 追溯矩阵

至少包含：

| 输入编号 | 输入原文摘要 | 类别 | PRD 去向 | 状态 |
|---|---|---|---|---|

状态只能为“已写入 / 仅保留为输入硬信息 / 被矛盾阻断 / 输入缺口”，不允许无说明遗漏。

## 验证与纠正

逐项检查并记录结果：

1. **文件存在**：`prd.md` 真实存在且非空。
2. **断言可追溯**：逐条扫描业务事实、数字、角色、规则和结论；每条能定位到 `source-ledger.md` 中的 `IN/CON/GAP`，或产物内有理由的 `DER/DSN/FIX`。
3. **无编造**：没有输入外的业务现状、功能、异常策略、指标或技术方案。
4. **硬信息完整**：输入硬信息逐项出现在正文或保留表；总数与输入事实清单一致。
5. **矛盾阻断**：每个 `CON-xxx` 已指出，受影响内容没有自动选边。
6. **优先级诚实**：没有依据的优先级全部是“未提供”。
7. **格式诚实**：最终只声明实际生成的 Markdown 文件。
8. **边界三点与公式求值**：对每个上限、下限、日期边界或枚举约束，列出“阈值前一档 / 等于阈值 / 越界一档”。数量变化动作先写 `after = before + delta`；逐行列出代入式、布尔结果和期望分支。若动作 `delta=+1` 且上限为 N，操作前允许条件必须等价于 `before < N`。强制回归代入 `before=N, delta=1`：`after=N+1`，所以 `after<=N` 为 `false`，必须走拒绝分支；不得写 `before <= N` 后又声称等于 N 时拒绝。
9. **收缩词反证**：搜索“仅、全部、所有、唯一、无额外、必须、不得”；逐条确认输入直接支持，否则删除或标成有理由的 DER/DSN/GAP。
10. **交接一致**：把角色、字段、数字、比较符、状态和阻断结果整理给负责人做跨产物终审；不得自行声称其他专员文件一致。

任一项失败时修改 `prd.md` 并从第 2 项重新检查。仍不能通过时把状态写成“部分完成”或“失败”，列出具体证据；禁止输出笼统的“自检全部通过”。
