# 产品需求方案 Agent 独立验收 Rubric

用途：验收产品 Agent 团队的共享证据账本、PRD、业务流程图和单 HTML 原型是否满足输入保真、职责分离、矛盾阻断与真实落盘要求。评估对象是“负责人 + 专职 Agent + preset + skill + 工具 + 验证”的完整 Harness，不采信团队成员的自评。 (ref: [[Agent评估]])

## 1. 评估输入

独立评估者只读取：

1. 原始脱敏测试输入和用户明确提供的全部脱敏附件；
2. 原始 `source-ledger.md`；
3. 三份原始产物文件；
4. 文件生成日志、Agent 委派/结算记录或工具结果；
5. 本 Rubric。

不要先提供预期分数、生成 Agent 的结论或疑似问题，避免评估者迎合。LLM Judge 只能补充语义判断，文件存在性、语法、字段计数和交互应优先使用机械证据。 (ref: [[LLM-as-a-Judge]])

## 2. 一票否决项

任一项成立，本次整体不得判“通过”：

- `source-ledger.md` 不存在、为空，或没有列出实际输入来源、所需产物和文件责任人；
- 三类目标产物中任一要求生成的文件不存在、为空，或只出现在对话中；
- 负责人未把任一目标产物委派给对应专职 Agent，却把结果声称为“产品 Agent 团队”交付；专职 Agent 越权覆盖账本或其他成员文件也不得通过；
- 任一未标注的业务事实、规则、数字、角色、字段、状态或异常策略无法在输入中找到来源；
- 任一输入硬信息既未出现在产物，也未明确标注为不进入该正文但已保留；
- 检测到输入矛盾后，任一产物擅自选择一方并让受影响流程或交互继续成功；
- 声称提供 PDF、DOCX、在线预览或临时链接，但实际没有对应文件/服务；
- Mermaid 无法解析，或 HTML/JavaScript 存在阻断使用的语法错误；
- 原型把测试夹具伪装成真实业务数据。
- 任一阈值、日期边界或数量上限的比较符方向错误，或把三点代入表达式所得布尔值与边标签/期望结果不一致；数字本身出现或列出三点表不算正确。数量变化动作必须按 `after = before + delta` 判断；强制回归点 `before=N, delta=1` 必须得到 `after=N+1`、`after<=N=false` 和拒绝分支。
- Agent 只取得工作区文件证据，却声称 hook、服务器 `raw/{工号}/`、数据库、控制台或 UI 展示已经成功；或把自然语言回执当成文件/上传成功的替代证据。

## 3. 分项评分

每项按 0–4 分评分。Rubric 要可理解、可分级、互不重复、可执行；不要因篇幅更长而加分。 (ref: [[LLM-as-a-Judge]])

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 | 4 分 |
|---|---|---|---|---|---|
| 输入事实保真 | 大量错误或改写 | 多处错误 | 少量实质错误 | 无实质错误，个别表达不精确 | 逐项准确且证据编号完整 |
| 硬信息覆盖 | 大量遗漏 | 遗漏关键项 | 有非关键遗漏 | 全覆盖但去向说明一般 | 全覆盖且逐项有正文去向 |
| 反编造与类别标注 | 大量无来源断言 | 多处未标注推断 | 偶有混类 | 无编造，类别基本清楚 | 五类边界稳定、推导理由充分 |
| 矛盾处理 | 未发现或自动选边 | 发现但仍执行 | 局部阻断 | 三产物均阻断 | 三产物阻断且影响/解除条件完整 |
| 三产物一致性 | 彼此冲突 | 多处不一致 | 少量不一致 | 事实与规则一致 | 编号、规则、状态、阻断完全对齐 |
| 团队编排与责任 | 无委派或文件互相覆盖 | 多项越权/未等待 | 有委派但交接不完整 | 分工、结算、终审均有证据 | 再加无重叠写入、失败回派和状态诚实 |
| 文件与格式诚实 | 未落盘/虚假承诺 | 多项不符 | 部分格式不符 | 三文件真实且声明基本准确 | 路径、格式、验证声明完全可复核 |
| 对接回执与边界 | 伪报服务器/UI成功 | 路径或 kind 大量错误 | 回执缺字段或边界含混 | 固定字段、路径和 kind 正确 | 再加证据层级与未验证项完全诚实 |
| 图表质量 | 不可解析/大幅编造 | 可解析但失真 | 基本可用 | 清晰且可追溯 | 结构、证据、阻断和可读性均优秀 |
| 原型质量 | 不可打开/核心交互坏 | 多数交互不可用 | 主路径可用 | 所需交互和阻断可用 | 再加证据面板、边界和可访问性验证 |

## 4. 机械检查优先级

1. 记录账本和三文件的相对路径、字节数和 SHA-256。
2. 从原始输入独立建立来源与硬信息清单，逐项核对账本的 `SRC/IN/CON/GAP`；账本本身不能作为输入事实的最终证明。
3. 从委派/结算记录核对任务类型、对应专员、完成时点和文件责任；文件最终内容与时间证据无法证明作者时写“未验证”，不得臆测。
4. 抽取每个产物的业务断言，标记来源编号和输入原文位置。
5. 解析全部 Mermaid 块。
6. 检查 HTML 外部资源、内联 JavaScript 语法、控件—处理逻辑对应关系。
7. 在浏览器中实际执行输入给出的正常、边界、异常与矛盾场景；无法执行的项目写“未验证”。
8. 对每个阈值建立“前一档 / 等于 / 越界一档”真值表；数量变化动作写 `after = before + delta`，逐行记录代入式、true/false、边标签和期望结果，四者不一致即失败。对每个上限 N 额外固定代入 `before=N, delta=1`，确认允许谓词为 false、拒绝分支为 true。再横向比较 PRD、图、原型，并反向搜索“仅/全部/所有/唯一/无额外/必须/不得”的直接证据。
9. 核对固定映射：`source-ledger.md -> other`、`prd.md -> prd`、`business-diagram.md -> diagram`、`prototype.html -> prototype`；检查最终回执字段与真实文件一致。工作区证据、hook 证据、服务器 raw 证据和 UI 证据分层记录，缺哪层就把哪层写“未验证”。
10. 最后才让 LLM Judge 按第 3 节补充语义评分，并保留其原始输出。

## 5. 判定规则

- **通过**：无一票否决项；所有维度 ≥3；输入事实保真、硬信息覆盖、反编造、矛盾处理四项均为 4。
- **部分通过**：无一票否决项，但存在维度为 2；必须列出返工项。
- **不通过**：出现一票否决项，或任一维度 ≤1。
- 单次通过只证明该样本通过，不代表稳定通过率；跨样本结论至少需要多个独立样本和重复运行。 (ref: [[Agent评估]])

## 6. 报告格式

```markdown
# 独立验收报告

## 结论
## 文件与机械证据
## 团队委派、结算与文件责任证据
## Agent 交付回执与 hook/raw/UI 边界
## 来源账本—原始输入核对
## 输入硬信息逐项去向
## 产出断言—输入证据表
## 矛盾发现与三产物阻断证据
## Mermaid 与 HTML/交互验证
## Rubric 分数与依据
## 未验证项
## 基线/迁移后差异
## CP3 自检：三类各验了什么
```

评估报告必须区分“负责人/专员自报”“委派与文件机械证据”“独立 Judge 判断”，不能把三者合并为一个未经核实的“全部通过”。
